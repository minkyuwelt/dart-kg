# 0006. 사람(임원) 식별자: 이름 + 생년월 + 성별

- 날짜: 2026-11-23
- 상태: 채택 (구현: `src/loaders/relations.py` `make_person_id`, `src/loaders/temporal.py` `rebuild_person`·`apply_person_merges`, `person` 테이블, `config/person_merges.csv`)
- 개정: 2026-11-23 병합 규칙 추가 (아래)
- 관련: 0002(회사 이름 → corp_code 연결, 엔티티 연결의 첫 사례), 0005(이중 시간축)

## 배경

임원 현황 API(`exctvSttus`)는 사람을 이름으로만 준다. 회사마다 따로 나오므로 "KB금융의 이재근"과 "국민은행의 이재근"이
같은 사람인지 데이터만으로는 알 수 없다. 그런데 이 프로젝트의 핵심 질문 중 하나가 **겸직**("지주 임원 중 자회사 임원을
겸하는 사람은?")이고, Phase 4 그래프에서 사람 노드를 회사 여러 곳에 잇는 것이 바로 이 판단이다.

회사는 corp_code라는 공식 식별자가 있어서 이름 연결(0002)이 "코드를 찾는 문제"였다. 사람은 공식 식별자가 없다.
그래서 **어떤 조합을 같은 사람으로 볼지**를 정해야 한다.

## 요구사항

| ID | 내용 |
|---|---|
| R1 | 같은 사람이 여러 회사·여러 보고서에 나와도 하나로 묶일 것 (겸직, 재직 이력) |
| R2 | 다른 사람을 하나로 잘못 묶는 일이 거의 없을 것. 잘못 묶이면 틀린 답이 "근거 공시"와 함께 나간다 |
| R3 | 규칙이 결정적일 것: 같은 입력이면 항상 같은 식별자. 재실행(rebuild)해도 식별자가 바뀌지 않을 것 |
| R4 | 응답에 있는 정보만 쓸 것. 외부 조회나 LLM 추측 없음 (0005와 같은 원칙) |
| R5 | 사람이 읽고 검증할 수 있을 것 |

## 응답이 주는 것 (tests/fixtures/exctvSttus_00688996_2025_11011.json)

이름 `nm`, 성별 `sexdstn`, 생년월 `birth_ym`('1961년 06월'), 직위, 등기 여부, 담당 업무, 주요 경력, 재직기간, 임기만료일.
주민번호나 사번 같은 고유 번호는 없다. 생년월일이 아니라 **생년월**이다.

## 후보

| 기준 | A. 이름만 | B. 이름 + 생년월 | **C. 이름 + 생년월 + 성별** | D. C + 경력 텍스트 유사도 |
|---|---|---|---|---|
| R1 같은 사람 묶기 | ◎ | ◎ | ◎ | ◎ |
| R2 다른 사람 안 묶기 | ✕ 흔한 이름(김영수 등)은 금융권에 여럿 | ○ 같은 이름·같은 달 출생은 드묾 | ○ B보다 조금 더 안전 | ◎ |
| R3 결정적 | ◎ | ◎ | ◎ | △ 경력 표기가 보고서마다 달라 임계값에 따라 갈림 |
| R4 응답만 사용 | ◎ | ◎ | ◎ | ◎ |
| R5 읽을 수 있음 | ◎ | ◎ | ◎ `양종희\|1961-06\|남` | ✕ 점수 |

## 결정: C

`person_id = 이름|생년월|성별` (예: `양종희|1961-06|남`). 값이 없으면 `?` (예: `홍길동|?|?`).

- 식별자를 해시가 아니라 **읽히는 문자열**로 둔다. 사람이 `person` 테이블을 보고 바로 검증할 수 있다 (R5)
- 같은 조합이 실제로 다른 사람일 가능성은 아주 낮지만 0은 아니다. **발견되면 이 문서에 수동 분리 규칙을 적고
  `config/`에 매핑을 둔다** (0002의 `corp_name_overrides.csv`와 같은 방식). 지금은 사례가 없어 만들지 않는다
- 생년월이 없는 행(`?`)은 이름만으로 묶이는 셈이라 R2가 약하다. `person.birth_ym IS NULL`인 행 수를 F 단계에서 확인한다
- D(경력 유사도)는 쓰지 않는다. 경력 표기가 보고서마다 달라 같은 사람도 점수가 흔들리고(R3), 결과를 설명하기 어렵다.
  C로 묶인 뒤 "같은 person_id인데 경력이 전혀 다른 경우"를 찾는 **검증 도구**로는 쓸 수 있다

## 구현

- `executive.person_id`: parse 단계에서 행마다 계산
- `person` 테이블: 닫기 단계(`rebuild_person`)가 정정되지 않은 executive 행에서 person_id마다 한 행을 만든다.
  `first_seen`(가장 이른 선임 시점 근사), `last_seen`, `corp_count`(임원으로 나온 회사 수, 2 이상이면 겸직 후보)
- 최대주주가 사람인 경우(`major_shareholder.nm`)는 생년월·성별이 없어 person과 잇지 않는다. 금융지주·은행의 최대주주는
  대부분 회사(지주, 국민연금공단)라 지금은 문제가 작다. 필요해지면 "같은 회사의 임원 중 이름이 같은 사람" 규칙을 검토한다

## 다시 판단할 조건

- F 단계 검증에서 같은 person_id가 다른 사람으로 확인되는 사례가 나오면 → 수동 분리 매핑 추가, 규칙에 직위·회사 조합 추가 검토
- 생년월 없는 임원 행이 많으면(예: 10% 이상) → 이름만으로 묶는 위험을 줄이기 위해 회사 안에서만 묶는 규칙으로 후퇴

## 개정 (2026-11-23): 원문 오타로 갈라진 사람 병합

F 단계 검증(임원 15,546행, 사람 1,710명)에서 **같은 이름·같은 출생연도인데 person_id가 다른 쌍 17개**가 나왔다. 원본 응답을 보니
파싱 문제가 아니라 **DART 제출 자료 자체가 보고서마다 다르게 적혀 있었다**: 같은 회사의 연속 보고서에서 출생월이 01↔10(7쌍), 04↔06 등으로
바뀌거나 성별이 남↔여(3쌍)로 바뀜. 예: 한윤철(제주은행) 2025 반기 '1968년 10월' → 2026 반기 '1968년 01월'. 민세진(신한라이프) 같은 해
두 보고서에서 '여'/'남'.

판단 기준(모두 만족해야 같은 사람으로 본다): 같은 회사, 같은 이름, 같은 출생연도, 월 또는 성별 하나만 다름, 보고서가 연속됨.
이 판단은 **사람이 하고** `config/person_merges.csv`에 쌍과 근거를 적는다 (R4: 코드가 추측하지 않는다. 회사 이름 매핑 `corp_name_overrides.csv`와 같은 방식).

어느 표기를 기준 id로 삼을지는 **코드가 규칙으로 정한다** (R3 결정성): 정정되지 않은 행이 많은 쪽, 같으면 더 최근 보고서에 나온 쪽.
원본 두 표기 중 어느 것이 맞는지는 공시만으로 알 수 없으므로 "더 많이/더 최근에 그렇게 적혔다"를 근거로 한다. 원래 id는 행의
nm·birth_ym·sexdstn에서 언제든 다시 계산할 수 있어 정보가 사라지지 않는다. `person.birth_ym`·`sexdstn`은 기준 id에서 읽는다.

병합하지 않는 것: 출생연도가 다른 동명이인(78건 중 61건), 회사가 다른 경우(겸직일 수도 있지만 오타 근거가 없다).

## 검증 결과 (2026-11-23)

- 생년월 없는 사람 0명 → 이름만으로 묶이는 위험 없음. "10% 이상이면 후퇴" 조건은 해당 없음
- 겸직 후보(corp_count ≥ 2) 204명. 지주 임원 ↔ 같은 지주 자회사 임원 36쌍이 알려진 겸직(지주 기타비상무이사 = 은행장 등)과 일치
- 같은 person_id가 다른 사람으로 확인된 사례: 없음
