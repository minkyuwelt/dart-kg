# 0005. 관계 데이터의 시간 표현: 이중 시간축(bi-temporal)

- 날짜: 2026-11-23
- 상태: 채택 (설계만. Phase 2 테이블을 만들 때 이 문서대로 구현한다)
- 관련: 0001(기술 스택) Phase 2~4, 0002(수집 대상)
- 참고: 0004는 노트북에서 진행 중인 Neo4j 한국어 전문검색 실험 기록으로 비워 둔다

## 배경

이 프로젝트의 목표는 "기업·주주·임원 **관계**를 지식그래프로 만들고 근거 공시와 함께 답하는 것"이다. 그런데 관계는 시간에 따라 바뀐다.

- 임원은 선임되고 퇴임한다. 겸직은 시작일과 종료일이 있다
- 최대주주 지분율은 변동한다. 자회사는 매각되거나 합병된다
- 정정 공시(`[기재정정]`)가 나오면 앞선 공시의 내용이 틀린 것이 된다

지금 있는 Phase 1 테이블은 공시 목록(`disclosure`)과 출자 스냅샷(`investment`)이라 이 문제가 드러나지 않았다. Phase 2에서 최대주주·임원 테이블을 만들기 전에, **시간을 어떻게 적을지**를 먼저 정해야 한다. 나중에 바꾸면 테이블을 다시 만들어야 하고(재호출은 안 해도 재정규화는 필요), Neo4j 그래프와 Q&A도 다시 만들어야 한다.

## 요구사항

| ID | 내용 | 근거 |
|---|---|---|
| R1 | 시점 질문에 답할 것: "2023년 3월 기준 신한은행 최대주주와 지분율은?", "2022년에 하나은행 사외이사였던 사람은?" | 프로젝트 목표. 현재 상태만 답하면 공시를 5년치 모으는 의미가 없다 |
| R2 | 정정 공시를 지우지 않고 반영할 것: 원래 공시와 정정 공시 둘 다 남기고, 답변은 정정된 사실을 쓰되 "무엇이 정정됐는지" 추적 가능할 것 | "근거 공시와 함께" 답하려면 근거의 이력이 남아야 한다 |
| R3 | 현재 상태 질문("지금 KB금융 자회사는?")은 추가 계산 없이 바로 답할 것 | 가장 흔한 질문 |

| R5 | 모든 시간 정보가 DuckDB 컬럼에 있어서 Neo4j를 언제든 다시 만들 수 있을 것 | CLAUDE.md 아키텍처 원칙 |
| R6 | 재실행해도 중복이 없을 것 (멱등) | CLAUDE.md 아키텍처 원칙 |

## 결정: C

관계를 나타내는 Phase 2 이후 테이블(최대주주, 임원, 출자)은 행마다 **두 종류의 시간**을 가진다. 이 구조는 Zep/Graphiti(arXiv 2501.13956)가 에이전트 메모리용으로 쓴 설계와 같다. 차이는 **시간을 LLM이 아니라 공시 제도에서 얻는다**는 점이다.

| 시간축 | 뜻 | 컬럼 | 값의 출처 |
|---|---|---|---|
| **사실 시간** (valid time) | 그 관계가 실제로 참이었던 기간 | `valid_from DATE NOT NULL`, `valid_to DATE NULL` (NULL = 아직 유효) | 공시가 주는 날짜 (아래 표) |
| **기록 시간** (transaction time) | 우리가 그 사실을 어느 공시로 알게 됐고, 어느 공시가 그것을 대체했는가 | `source_rcept_no VARCHAR NOT NULL`, `superseded_by VARCHAR NULL` | 접수번호. 접수일은 `disclosure.rcept_dt`로 조인 |

- **지우지 않는다.** 사실이 끝나면 `valid_to`를 채우고, 정정되면 `superseded_by`를 채운다. 행은 남는다
- **현재 상태 뷰**: `valid_to IS NULL AND superseded_by IS NULL`
- **시점 질의** (날짜 d 기준): `valid_from <= d AND (valid_to IS NULL OR valid_to > d) AND superseded_by IS NULL`
- **"그때 알려진 대로" 질의**(선택): 위 조건에 `source의 rcept_dt <= d`를 더하면 "d 시점에 공시로 알 수 있었던 것"만 남는다. 정정 전 사실을 포함하므로 기본 질의에는 쓰지 않는다

### 사실 시간을 어디서 얻는가

DART 정기보고서 주요정보 API별로, `valid_from`과 `valid_to`를 채우는 규칙이다. 필드 이름은 OpenDART 개발가이드 기준이며, **노트북에서 실제 응답으로 확인한 뒤 구현한다** (확인 필요).

| 관계 | API | `valid_from` | `valid_to` 닫는 규칙 | 해상도 |
|---|---|---|---|---|
| 회사 → 출자 대상 (지분율) | 타법인 출자현황 `otrCprInvstmntSttus` | 최초 취득일 `frst_acqs_de`. 없으면 보고서 기준일 `stlm_dt` | 다음 정기보고서에 같은 출자 대상이 없으면 그 보고서의 `stlm_dt` | 분기 (지분율 값은 보고서마다 바뀌므로 보고서 단위 행 유지) |
| 회사 → 최대주주 (지분율) | 최대주주 현황 `hyslrSttus` | 보고서 기준일 `stlm_dt` | 다음 보고서에 없으면 그 보고서의 `stlm_dt` | 분기 |
| 회사 → 최대주주 **변동** | 최대주주 변동현황 `hyslrChgSttus` | 변동일 `change_on` | 다음 변동 행의 `change_on` | **일** (가장 정확. 분기 사이 변동을 여기서 얻는다) |
| 회사 → 임원 (직위, 겸직) | 임원 현황 `exctvSttus` | 보고서 기준일 `stlm_dt`. 재직기간 `hffc_pd`("3년 11개월")가 있으면 역산해 월 단위로 앞당김 | 다음 보고서에 같은 사람·직위가 없으면 그 보고서의 `stlm_dt`. 임기만료일 `tenure_end_on`이 더 이르면 그 날짜 | 분기 (역산은 월) |

- "다음 정기보고서"는 같은 회사의 사업·반기·분기보고서 중 `stlm_dt`가 바로 다음인 것이다. **보고서 하나가 수집에서 빠지면 관계가 잘못 닫히거나 늦게 닫힌다.** 그래서 닫기는 적재 때 한 번 정하지 않고, 테이블 전체를 원본 응답(`raw_api_response`)에서 다시 만들 때마다 다시 계산한다 (`investment`의 `rebuild`와 같은 방식)
- 보고서 사이의 변동 중 공시가 날짜를 주는 것(최대주주 변동, 최초 취득일)만 일 단위다. 나머지는 "보고서 기준일에 참이었다"까지만 안다. 답변에서도 그렇게 말해야 한다 ("2025년 6월 말 기준")

### 기록 시간: 정정 공시 처리

- 정정 공시(`report_nm`이 `[기재정정]`으로 시작, `disclosure.rm`에 '정')가 들어오면, **같은 회사·같은 보고서 기간**의 원본 공시에서 나온 행 전부에 `superseded_by = 정정 접수번호`를 적는다. 정정 공시에서 새로 뽑은 행이 그 자리를 대신한다
- 원본 행은 남으므로 "무엇이 정정됐는가"는 두 접수번호의 행을 비교하면 나온다 (R2)
- 정정 공시를 어느 원본과 짝짓는지는 `rcept_no`가 아니라 **회사 + 보고서 종류 + 사업연도**로 한다. DART의 정기보고서 주요정보 API는 `bsns_year`+`reprt_code`로 조회해 최신(정정 반영) 응답을 주므로, 원본·정정 짝짓기는 `disclosure` 목록에서 한다 (확인 필요: 정정 전 응답을 API가 여전히 주는지. 안 주면 원본 행은 정정 전에 수집된 `raw_api_response`에만 남는다)

### 공통 컬럼 (Phase 2 관계 테이블 규칙)

```sql
-- 모든 관계 테이블이 갖는 컬럼. 나머지는 관계마다 다르다.
source_rcept_no  VARCHAR  NOT NULL,  -- 이 행을 뽑은 공시 (기록 시간 시작)
row_seq          INTEGER  NOT NULL,  -- 응답 안 행 순서 (investment와 같은 이유)
valid_from       DATE     NOT NULL,  -- 사실 시간 시작
valid_to         DATE,               -- 사실 시간 끝. NULL이면 유효
superseded_by    VARCHAR,            -- 이 행을 대체한 정정 공시 접수번호. NULL이면 유효
loaded_at        TIMESTAMPTZ NOT NULL,
PRIMARY KEY (source_rcept_no, row_seq)
```

- 기본키에 공시 접수번호가 들어가므로 같은 공시를 다시 적재해도 같은 행을 덮어쓴다 (R6)
- `valid_to`·`superseded_by`는 적재 후 **rebuild 단계**에서 규칙으로 채운다. 행을 뽑는 함수와 닫는 함수를 분리해 각각 테스트한다
- 지금 있는 `investment` 테이블은 B(스냅샷)다. Phase 2에서 위 컬럼을 더해 C로 올린다. 원본 응답이 다 있으므로 API 재호출 없이 가능하다

### Neo4j에서는

엣지 속성으로 그대로 옮긴다. 관계 하나가 시간에 따라 여러 번 바뀌면 엣지가 여러 개 생기고, 각 엣지가 `valid_from`·`valid_to`·`rcept_no`를 가진다.

```cypher
// 2023-03-31 기준 신한은행의 최대주주
MATCH (c:Corp {corp_code: $code})-[r:MAJOR_SHAREHOLDER]->(s)
WHERE r.valid_from <= date('2023-03-31')
  AND (r.valid_to IS NULL OR r.valid_to > date('2023-03-31'))
  AND r.superseded_by IS NULL
RETURN s.name, r.stake_pct, r.rcept_no
```

`r.rcept_no`가 답변에 붙는 근거 공시다. Phase 4(GraphRAG)에서 "2022년에 하나은행 사외이사였던 사람이 지금 다른 자회사 임원인가" 같은 질문이 이 필터 하나로 경로 탐색이 된다. 이런 **시점이 섞인 다중 경로 질문**이 벡터 검색만으로는 못 풀고 그래프가 필요한 질문이다 (GraphRAG 벤치마크들이 그래프가 이기는 영역으로 꼽는 유형).

## 하지 않기로 한 것

- **Graphiti 라이브러리 도입**: 새 사실이 들어올 때마다 LLM에게 "기존 사실과 충돌하는가"를 물어 `invalid_at`을 닫는다. 우리는 공시가 날짜와 보고서 기간을 주므로 규칙으로 닫을 수 있고, 그래야 틀렸을 때 추적할 수 있다 (R4). 설계만 가져온다
- **스냅샷마다 그래프 따로 만들기**: 시점 수만큼 그래프가 생겨 Neo4j 재생성과 질의가 복잡해진다

## 비용·리스크

- 구현: Phase 2 적재 함수에 닫기 규칙과 테스트가 추가된다. API 호출 수는 0002의 Phase 2 추정(약 1,800건)과 같다. 최대주주 변동현황을 더 쓰면 보고서당 1건이 더 든다 (30곳 × 연 4회 × 5년 = 600건, 한도 안)
- 재직기간 역산은 월 단위라 실제 선임일과 최대 한 달 차이 난다. 정확한 선임일이 필요하면 "임원 선임·해임" 수시공시를 Phase 2 뒤에 추가한다
- 정기보고서를 내지 않는 자회사 29곳(0002)은 관계 데이터가 없다. 지주의 출자 데이터에 노드로만 들어간다 (0002와 같음)
- 동명이인 임원(같은 이름이 여러 회사에 있을 때 같은 사람인지)은 이 문서의 범위가 아니다. 사람 식별자는 Phase 2 엔티티 연결 결정(0006 예정)에서 정한다. 이 문서는 "관계마다 시간이 있다"만 정한다

## 다시 판단할 조건

- 정기보고서 주요정보 API가 정정 전 응답을 주지 않아 R2를 `disclosure` 목록만으로 만족시킬 수 없으면 → 정정 공시 원문(Phase 3)에서 정정 내용을 뽑는 방법을 검토
- 시점 질문 평가셋(Phase 3에서 만들 골든셋)에서 분기 해상도가 부족하다고 나오면 → 수시공시(임원 선임, 최대주주 변경) 수집을 추가
