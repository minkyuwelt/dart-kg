# 0001. 기술 스택: DuckDB + Dagster + Neo4j

- 날짜: 2026-11-23
- 상태: 채택
- 대체한 결정: 초기 구상(PostgreSQL + pgvector + Airflow + Neo4j). PR #5(Airflow + PostgreSQL docker-compose)는 노트북 검증까지 마쳤지만 이 결정에 따라 병합하지 않고 닫음

## 배경

초기 구상의 PostgreSQL·Airflow는 프로젝트 요구사항에서 출발해 고른 것이 아니었다. 아래 요구사항을 먼저 정리하고, 결정마다 후보를 비교해 다시 골랐다. "많이 쓰인다", "써 본 적 있다/없다"는 판단 기준에서 뺐다.

## 요구사항

| ID | 내용 | 기술 선택에 주는 영향 |
|---|---|---|
| F1 | 공시 목록·기업개황을 매일 수집 | DART `list.json`은 날짜 구간(bgn_de~end_de) 조회. 빠진 날을 구간 단위로 다시 채워야 함 |
| F2 | 최대주주·임원·타법인 출자 (정기보고서 기준 시점별 스냅샷) | 정형 데이터이고 보고서 기준일이라는 시점 축이 있음 |
| F3 | 공시 원문 → 청크 → 임베딩 → 검색 | 단계가 길고 임베딩은 비용이 듦. 실패한 단계만 다시 실행해야 함 |
| F4 | 지주 → 자회사 → 손자회사 다단계 지분, 임원 겸직 탐색 | 관계·경로 질의 |
| F5 | 자연어 질문에 근거 공시(rcept_no)와 함께 답변 | 텍스트 근거와 관계 그래프를 함께 탐색해야 함 (이 프로젝트의 핵심) |
| N1 | 규모가 작음: 공시 대상 회사 약 60곳(추정, 확인 필요), 정기보고서 약 1,200건(5년) | 대용량 전용 도구가 필요 없음 |
| N2 | 멱등 적재 | upsert와 중복 검사가 쉬워야 함 |
| N4 | API 한도 하루 약 20,000건 | 원본 응답을 보관해 두면 스키마를 바꿔도 다시 호출하지 않아도 됨 |
| C1 | 실행 환경은 학원 노트북 (항상 켜져 있지 않음, 다른 수업 프로젝트 컨테이너가 5432·8080·7474·7687을 쓰는 중) | 서버를 여럿 띄울수록 운영 부담과 포트 충돌이 늘어남 |
| C2 | 노트북은 과정이 끝나면 반납 | 로컬 데이터는 코드만으로 다시 만들 수 있어야 함 |

전체 재수집 호출 수(추정): 기업개황 60 + 공시 목록 약 180 + Phase 2(3종 × 연 4회 × 5년 × 60곳) 3,600 + 원문 1,200 = **약 5,000건**. 하루 한도 안이므로 로컬 DB를 잃어도 하루면 다시 만들 수 있다(C2).

## 결정 1: 저장소 구조 — 벡터와 그래프를 Neo4j에 모은다

저장소는 따로 고를 수 없다. 벡터와 그래프를 어디에 두느냐에 따라 원본 저장소가 해야 할 일이 달라지기 때문이다.

| | 구조 X (초기안) | **구조 Y (채택)** |
|---|---|---|
| 원본 | PostgreSQL (정형 + pgvector) | 파일 DB (정형 + 원본 응답 JSON) |
| 그래프 | Neo4j (PostgreSQL에서 파생) | Neo4j (그래프 + 벡터 + 전문검색) |
| GraphRAG 검색 (F5) | PostgreSQL에서 벡터 검색 → corp_code로 Neo4j 조회 → 앱에서 합침 | 벡터로 찾은 공시 청크 → `MENTIONS` 관계로 회사·임원 노드 → 지분 경로까지 Cypher 하나로 탐색 |

**채택 이유:** F5는 텍스트 근거에서 출발해 관계 그래프를 타는 검색이다. 둘이 같은 저장소에 있으면 질의 하나로 처리할 수 있다. Neo4j가 이 패턴을 공식 라이브러리로 제공하고(neo4j-graphrag의 VectorCypherRetriever), Community 에디션에서도 벡터 인덱스를 지원한다.

**X가 나았을 조건:** 그래프 없이 RAG만 할 때, 또는 Neo4j에서 한국어 검색 품질이 나오지 않을 때.

## 결정 2: 원본 저장소 — DuckDB

구조 Y에서 원본 저장소에 남는 일은 "작은 정형 테이블과 원본 응답을 보관하고, 거기서 그래프를 다시 만든다"뿐이다.

| 기준 | SQLite | **DuckDB** | PostgreSQL |
|---|---|---|---|
| F2 시점별 정형 테이블, N2 upsert | ◎ | ◎ (`INSERT ... ON CONFLICT`) | ◎ |
| 원본 응답 JSON 보관 후 SQL로 다시 정규화 (N4) | ○ JSON1 | ◎ `read_json`, 중첩 타입 | ◎ jsonb |
| 시점별 지분 변화 같은 분석 질의 | ○ | ◎ 열 지향 | ○ |
| 쓰는 도중에 다른 프로세스에서 읽기 | ◎ WAL | ✕ 파일 잠금 (읽기 전용 연결도 쓰기와 동시에 못 엶) | ◎ |
| 운영 (C1·C2) | 파일 하나 | 파일 하나 | 서버(컨테이너) |

**채택 이유:** 벡터를 Neo4j로 보내면 PostgreSQL에만 있는 기능을 쓸 일이 없다. 기능이 같다면 서버가 없는 쪽이 낫다(C1). 파일 DB 둘 중에서는 원본 JSON을 SQL로 다시 정규화하는 작업(N4)과 지분 추이 분석(F2)에 강한 DuckDB를 골랐다. **SQLite와의 차이는 작다.**

**단점 대응:** 쓰기를 한 프로세스만 할 수 있다 → Dagster에서 DuckDB에 쓰는 자산은 한 번에 하나씩 실행되도록 설정한다. ~~파이프라인이 도는 동안 노트북에서는 읽기 전용으로 연결한다.~~

> **정정 (2026-11-23):** 읽기 전용 연결로는 해결되지 않는다. DuckDB는 파일을 프로세스 단위로 잠가서, 다른 프로세스가 읽기 전용으로 열고 있어도 쓰기 연결을 열 수 없고 그 반대도 마찬가지다 (duckdb 1.5.6에서 확인). 대응을 바꿨다: 노트북은 `with` 블록으로 열고 바로 닫으며, Dagster 자산은 잠금에 걸리면 몇 분 뒤 다시 시도한다. 결정 자체는 유지한다. 이 프로젝트의 쓰기는 하루 한 번 몇 초뿐이라 잠금이 겹칠 일이 적고, 겹쳐도 재시도로 해결된다.

**다른 후보가 나았을 조건:** PostgreSQL은 벡터를 원본 저장소에 둘 때나 쓰는 프로세스가 여럿일 때. SQLite는 분석 질의가 거의 없을 때.

## 결정 3: 파이프라인 — Dagster

파이프라인이 실제로 해야 하는 일: 매일 증분 수집(F1), 노트북이 꺼져 있던 날 채우기(C1), 실패한 단계만 재실행(F3), **원본이 바뀌면 그래프·임베딩 재생성**(아키텍처 원칙).

| 기준 | cron + CLI 스크립트 | Airflow | **Dagster** |
|---|---|---|---|
| 파생 데이터 재생성 | 직접 관리 | 작업(task) 중심이라 산출물 간 관계는 별도로 관리 | 자산 간 의존 관계가 기본 모델. 원본이 바뀌면 영향받는 자산이 표시됨 |
| 날짜·회사 단위 재처리 | 직접 구현 | 날짜 구간(data interval) 단위 | 날짜 파티션 + corp_code 파티션 |
| 품질 검사 (rcept_no 중복, 지분율 합 ≤ 100%) | 직접 구현 | 별도 작업 | asset check로 자산에 붙임 |
| 노트북 운영 부담 | 없음 | 메타DB 서버, JWT, 컨테이너 (실측 RAM 1.2GB) | `dagster dev` 한 프로세스 |

**채택 이유:** 이 프로젝트의 데이터는 원본 → 정규화 테이블 → 그래프·임베딩으로 파생된다. 재생성 원칙을 코드로 표현하는 데에는 작업 순서보다 자산 의존 관계가 직접적이다.

**단순한 대안 테스트:** Phase 1만 보면 cron으로 충분하다. cron이 막히는 지점은 Phase 3~4다. "정규화 규칙을 고쳤으니 영향받는 그래프·임베딩만 다시 만든다"를 직접 구현해야 한다.

**리스크:** 2026년 7월 Prefect가 Dagster Labs 인수를 발표했다. 공식 FAQ에 따르면 오픈소스 릴리스는 계속된다. 대응: 수집·적재 로직은 Dagster에 의존하지 않는 일반 함수로 만들고, Dagster 자산은 그 함수를 호출만 한다. 바꿔야 하면 그 층만 갈아끼운다.

**cron이 나았을 조건:** Phase 3~4를 하지 않을 때.

## 고르지 않은 것

- **dbt:** 변환 모델이 많아야 10개 안팎이고, 테스트는 Dagster asset check로 충분하다. 변환 모델이 20개를 넘으면 다시 판단한다.
- **Kùzu (임베디드 그래프 DB):** DuckDB와 궁합이 좋지만 2025년 10월 저장소가 보관(archived) 처리되어 개발이 멈췄다.
- **DuckDB vss 확장 (DuckDB 안의 벡터 검색):** 인덱스 영속화가 아직 실험 기능이고, 공식 문서도 운영 사용을 권하지 않는다.

## 확인이 필요한 것

- **Neo4j 전문검색의 한국어 처리:** Lucene에는 CJK 분석기가 있지만, Neo4j에서 쓸 수 있고 품질이 충분한지는 Phase 3에서 작은 실험으로 확인한다. 부족하면 앱에서 형태소 분석 후 색인하는 방식으로 보완한다.
  - **확인 (2026-11-23):** 작은 실험으로 확인했다 → `0004-korean-fulltext.md`. 한국어 형태소 분석기(nori)는 없지만, `cjk` 분석기 + 구절 검색 + 경계 전처리(가운뎃점·영문/숫자와 한글 사이 공백)로 검색어 19개에서 재현율 97%, 정밀도 93%. 앱 형태소 분석(kiwipiepy) 방식은 재현율 79%로 채택하지 않음. 구조 Y 유지. 실제 원문으로는 Phase 3에서 다시 확인한다
- **대상 회사 수(N1):** 실제 자회사 목록으로 호출 수를 다시 계산한다.

## 이 결정보다 더 중요한 결정 (Phase 2~3에서 따로 기록)

1. **엔티티 연결:** 최대주주·임원 데이터에는 corp_code가 없고 이름만 있다. 동명이인 임원, 같은 회사의 다른 표기를 어떻게 묶을지가 그래프 정확도를 정한다.
2. **공시 원문 파싱·청킹:** DART 원문은 자체 XML 형식이다. 섹션 단위로 자르는 방식이 RAG 근거 품질을 정한다.
