# 0008. 공시 원문 청킹 (조각 단위·표 처리·꼬리표)

- 상태: **초안** (2026-11-24). 확정은 6번 PR에서 임베딩 모델과 함께 평가 세트 숫자를 보고
- 관련: `docs/plans/phase3.md` (B)절, `docs/decisions/0007-xml-parser.md`(섹션·표가 어떻게 생기는지), `eval/`(비교 기준)

## 배경

파싱 결과(0007 5차)는 사업보고서 188건에 섹션 15,059개, 표 217,001개, 글자 약 5,000만이다. 섹션 하나가 수천 자(회계정책 주석 4만 자),
표 수백 개인 것도 있어 임베딩 모델이 한 번에 읽는 길이(수백 토큰)를 크게 넘는다. 그래서 섹션을 조각으로 잘라야 하는데,
자르는 방식은 검색 품질을 좌우하는 변수라 결정 기록으로 남긴다. 판단 기준은 평가 세트(`eval/questions.jsonl`, ready 41개)의 hit@5·MRR이다.

## 결정할 것과 후보

### 1. 조각 단위

| 전략 | 뜻 | 기대 | 걱정 |
|---|---|---|---|
| `fixed` | 섹션 무시, 파일 전체 글을 이어서 1,000자마다 자름 | 가장 단순. 다른 전략이 이것보다 나은지 재는 기본선 | 섹션 경계·표가 잘림, 문맥이 끊김 |
| `section` | 섹션이 울타리. 짧으면 통째로, 길면 문단 경계에서 1,000자 안팎으로 묶고 앞 문단 하나 겹침. 표는 글과 따로 조각 | 조각이 하나의 주제를 가짐. 근거 섹션 단위 평가와 맞음 | 짧은 섹션은 조각이 짧아 문맥이 적음 |
| `section_path` | `section` + 임베딩용 글 앞에 "회사명 \| 보고서 \| 섹션 경로" | 짧은 조각도 "어느 회사·어느 항목"을 가짐. 키워드 기본선에서 회사를 못 가린 문제(hit@5 0.28)에 직접 대응 | 꼬리표가 임베딩을 지배해 본문이 묻힐 수 있음 → 실험으로 확인 |

제외한 것(조사 `phase3-research.md`): 의미 기반 청킹(조각이 너무 짧아짐, 모델 의존), 문단 단위(공시 문단은 한 줄짜리가 많음).

### 2. 크기

**1,000자** (사용자 결정 2026-11-24). 한국어 토큰으로 어림 500~600. 토큰 수는 임베딩 모델마다 달라 모델이 정해지는 0009에서 그 토크나이저로 다시 잰다.
글자 수로 자르는 이유는 모델을 바꿔도 조각이 그대로여서 비교가 공정하기 때문. 500자 조합은 0009에서 필요하면 추가.

### 3. 표 처리

| 후보 | 판단 |
|---|---|
| 통째로 텍스트 | 표가 길면(임원 표 30행 × 13열) 한 조각이 수천 자 → 제외 |
| **행마다 "열이름: 값"** (채택) | 머리행(여러 줄이면 위에서 아래로 이어 "기말잔액 장부가액")을 열 이름으로, 행마다 "성명: 정진완 \| 성별: 남 \| …". 1,000자 안에 드는 만큼 행을 묶어 한 조각. 표 하나는 쪼개도 행은 쪼개지 않는다. 캡션·단위는 첫 줄 "[표] 캡션 (단위)" |
| 표는 빼고 Phase 2 정형 데이터에 맡김 | 임원·최대주주·출자 표에만 가능. 배당·직원·위원회 표는 정형 데이터가 없음 → 제외. 다만 Phase 4에서 이 세 표는 그래프 쪽이 답한다 |

표 조각은 `kind='table'`로 구분해 실험에서 글/표를 따로 볼 수 있다. 재무제표 주석(`is_note`)은 조각 수의 큰 몫인데(표 21만 중 대부분) 평가 질문 41개 중
주석에 답이 있는 것은 2개뿐이다 → 주석을 빼면 hit@5가 오르고 조각 수가 줄어드는지 0009에서 함께 본다.

### 4. 조각에 붙이는 정보 (chunk 테이블 열)

회사 코드·회사명(공시 당시)·보고서명(`disclosure`에서), 섹션 경로, 주석 여부, 글/표, 표 번호, 전략, 글자 수, embed_text 해시(재임베딩 때 바뀐 조각만).
`chunk_id = '{strategy}:{rcept_no}:{file_name}:{seq}'`는 Neo4j 노드 키로도 쓴다. 기준일은 `report_nm`("사업보고서 (2025.12)")에서 읽을 수 있어 열을 따로 두지 않았다.

## 구현

- `src/loaders/chunking.py`: 순수 함수 (`chunk_sections(meta, sections, strategy)`). DuckDB를 모른다
- `src/loaders/chunks.py`: `document_section` → `chunk` (전략·접수번호 단위로 지우고 다시 넣음 → 멱등). CLI `build / stats / show`
- `eval/retrievers/chunk.py`: 조각 위의 키워드 검색 `--retriever chunk:<전략>`. 임베딩 전에 전략을 같은 규칙으로 비교
- 기본은 본문 파일만. 첨부(감사보고서)는 `--attachments`

## 1차 실험 계획 (5번 PR, 노트북)

대상: 평가 세트 근거 보고서 전부(약 30개, `--from-eval`. 사용자 결정 2026-11-24 — 계획의 "지주 4 + 자회사 26"보다 비교에 직접적).

```
python -m src.loaders.chunks build --strategy all --from-eval
python -m src.loaders.chunks stats
python -m eval.run --retrieval-only --retriever chunk:fixed --label fixed
python -m eval.run --retrieval-only --retriever chunk:section --label section
python -m eval.run --retrieval-only --retriever chunk:section_path --label section_path
```

볼 것: 전략별 조각 수·길이 분포(표/글, 주석 비율), 섹션 기준 hit@5·MRR. 키워드 검색이라 절대값은 낮겠지만 **전략 사이의 차이**가 보이면
0009 임베딩 실험에서 전략 수를 줄일 수 있다.

## 다시 판단할 조건

- `section_path`의 꼬리표가 본문을 묻어 본문 질문(서술형) 점수가 `section`보다 낮으면 → 꼬리표를 짧게(경로만) 하거나 메타데이터 필터로 옮긴다
- 표 조각이 전체의 80%를 넘고 표 질문 점수에 기여하지 않으면 → 주석 표를 임베딩에서 빼고 전문검색(Neo4j fulltext)에만 둔다
- 0009에서 토큰 수를 재어 1,000자가 모델 한도(예: 512 토큰)를 자주 넘으면 → 800자로 줄인다
