# 0011. 그래프 스키마와 GraphRAG: 질문 12개 → 노드·관계 → 고정 템플릿

날짜: 2026-11-25 · 상태: **초안** (구조는 사용자 결정. 질문 12개의 정답 확인과 측정 결과는 노트북에서 채운다) · 관련: 0005 이중 시간축, 0006 사람 식별, `docs/plans/phase3.md` 11절, `docs/plans/phase4-research.md`(조사), `docs/plans/usecases.md` 2절

**한 줄 요약:** DuckDB에서 검증한 관계 테이블을 그대로 노드 4종·관계 5종으로 옮기고, 질문은 라우터가 고정 Cypher 템플릿 8개 중 하나로 보내며, 그 결과를 공시 글 검색과 RRF로 합친다. LLM은 관계를 뽑지도, Cypher를 쓰지도 않는다.

## 요구사항

usecases 2절의 업무 질문 11개 중 Phase 3 검색(RAG)으로 답할 수 없는 것이 넷이다: 2(임원 이력), 3(겸직), 5(직접·간접 지분), 9(사명이 바뀐 회사).
넷 다 "표 한 장에서 행을 찾는 것"이 아니라 **연결을 따라가야** 답이 나온다. 조각 검색은 연결을 모르므로 이 질문들에서 0점에 가까울 것이다(phase3.md 4절).
그래서 이 결정의 시험지는 아래 질문 12개다. 스키마와 템플릿은 **이 12개에 답할 만큼만** 만들고, 더 커지지 않게 한다.

## 결정 2. 노드와 관계

phase3.md 11절 그대로다. 조사(phase4-research 5절 1)에서 이 범위를 넘는 필요가 나오지 않았다.

| 노드 | 키 | 출처 (DuckDB) | 속성 |
|---|---|---|---|
| `Corp` | `corp_code` (없으면 `name:{보고한 회사 corp_code}:{정규화 이름}`, ②·⑤) | `corp`, `target_corp`, `investment`, `major_shareholder` | `name`(지금 이름), `names`(공시에 나온 이름 목록, ①), `role`(holding/subsidiary/null), `has_corp_code` |
| `Person` | `pid` = `person_id`(0006)의 해시 앞 16자리 | `person` | `name`만. **생년월·성별은 올리지 않는다** (식별에만 쓰고 표시하지 않음, 0006·0012). `person_id`를 키로 그대로 쓰면 그 안의 생년월이 질의 결과로 샐 수 있어 해시로 바꾼다 |
| `Document` | `rcept_no` | `disclosure`, `document` | 이미 Phase 3에서 생김 |
| `Chunk` | `chunk_id` | `chunk` | 이미 Phase 3에서 생김 |

| 관계 | 방향 | 출처 | 속성 (시간 4개는 모든 관계 공통) |
|---|---|---|---|
| `OWNS` | 주주 → 회사 | `investment`(출자한 회사의 보고서), `major_shareholder`(출자받은 회사의 보고서) | `pct`, `shares`, `book_value`(출자만), `share_class`, `source_table` |
| `HOLDS_POSITION` | Person → Corp | `executive` | `title`(직위), `registered`(등기 구분), `outside`(사외이사 여부), `full_time` |
| `FILED` | Corp → Document | `disclosure` | (시간 속성 없음: 공시 사실 자체) |
| `HAS_CHUNK` | Document → Chunk | `chunk` | (이미 있음) |
| `FORMERLY` | 지금 회사 → 옛 회사 | `config/corp_lineage.csv` (사람이 근거와 함께 적음) | `on`(합병·변경일), `reason`, `evidence_rcept_no` |

- **시간 속성 4개:** `valid_from`·`valid_to`·`source_rcept_no`·`superseded_by`. DuckDB 행의 값을 그대로 옮기고 Neo4j에서 다시 계산하지 않는다(0005). 각 시간 속성에 관계 범위 인덱스를 만든다.
- **행 하나 = 관계 하나.** DuckDB의 `(source_rcept_no, row_seq)`를 관계 키(`row_key`)로 두어, 몇 번을 다시 올려도 중복이 생기지 않는다(MERGE). 보고서마다 같은 사람의 같은 직위가 반복되지만 합치지 않는다 — 합치는 것은 "언제부터 언제까지 재직"이라는 **파생** 값이고, 그건 템플릿(T5)이 질의할 때 계산한다.
- **`OWNS` 하나에 출처 둘.** KB금융→국민은행 지분은 KB금융의 출자 표와 국민은행의 최대주주 표에 각각 나온다. 관계 이름을 둘로 나누면 "위로 따라가기(T1)"와 "아래로 따라가기(T2)"가 다른 관계를 봐야 해서 경로 질의가 두 배가 된다. 하나로 두고 `source_table`로 구분한다. 두 값이 다르면 그것 자체가 확인할 거리다(같은 날짜의 두 공시가 다른 지분율을 적은 것).

**미결 다섯 가지와 결정 (사용자 결정 2026-11-25, 추천대로):**

| | 질문 | 결정 | 이유 |
|---|---|---|---|
| ① | 사명 변경·합병 | corp_code가 같으면 노드 하나에 이름 목록(`names`). corp_code가 바뀐 경우만 `FORMERLY` | corp_code가 회사 식별자라는 원칙(CLAUDE.md). 이름이 바뀌어도 같은 법인이면 같은 노드여야 시점 질의가 끊기지 않는다 |
| ② | corp_code 없는 출자 대상(해외 법인·펀드) | 같은 `Corp` 라벨, 키는 `name:`+정규화 이름, `has_corp_code=false` | "지주의 출자 대상 전부"를 탐색 한 번으로 얻는다. 라벨을 나누면 T2·T3마다 두 경우를 따로 써야 한다. 이름 키에 **보고한 회사**를 넣어, 다른 회사 표에 나온 같은 이름과도 합치지 않는다(개인 주주 동명이인 때문. 대신 두 자회사가 같은 해외 펀드에 출자하면 노드가 둘 — g06에서 셀 때 주의) |
| ③ | 특수관계인 관계 | 보류 | 질문 11개·그래프 질문 12개 중 이 관계가 필요한 것이 없다. 최대주주 표의 `relate` 값은 `OWNS` 속성으로만 남긴다 |
| ④ | 연도·분기 보조 노드 | 만들지 않음 | 관계의 시간 속성 필터로 "그 시점 그래프"를 얻는다(phase4-research 1.3). 노드를 두면 같은 날짜를 두 곳에 적게 된다 |
| ⑤ | corp_code 없는 **최대주주**(국민연금·우리사주조합·개인 등) | ②와 같은 이름 노드(`Corp` 라벨, `has_corp_code=false`). 개인 주주도 `Person`에 잇지 않는다 | 최대주주 표에는 생년월이 없어 `person_id`를 만들 수 없다. 이름이 같다고 임원 `Person`과 이으면 추측이다(0006). 라벨이 `Corp`인 것이 어색하지만, 질문 g01처럼 "체인 끝에 누가 있나"만 보면 되므로 탐색을 하나로 두는 쪽을 택했다 — 이 항목은 초안에서 새로 나온 것이라 PR에서 의견을 묻는다 |

**다시 만들기 (2026-11-25, `feat/graph-relations`):** 관계 층(Corp·Person과 그 관계)은 적재할 때마다 지우고 통째로 다시 넣는다. DuckDB 관계 테이블도 rebuild로 통째로 다시 만들어져 행이 사라질 수 있는데, MERGE만 하면 사라진 행이 Neo4j에 남기 때문이다. 수만 행이라 몇 초면 된다. 조각 층(Document·Chunk)은 건드리지 않는다. `FILED`는 이미 있는 Document에만 잇는다.

## 결정 3. 세 층 (사실 / 파생 / 해석)

- **사실:** 위 노드·관계 전부. 공시 값 그대로.
- **파생:** 간접 지분율(경로 지분율의 곱), "자회사를 거쳐서만" 판정, 재직 기간 합치기, 겸직 묶음. **저장하지 않고** 템플릿이 질의할 때 계산해 결과 행에 `rule` 이름을 붙인다. 저장하지 않는 이유: 사실 층이 바뀌면(정정 공시) 파생 값이 저절로 따라 바뀐다. 계산이 느려지면 그때 `derived_from`·`rule`을 붙여 저장한다.
- **해석:** LLM의 판단("지배한다", "건전하다"). 그래프에 넣지 않고 답변 단계에서만.

## 결정 4. 질의: 라우터 + 고정 템플릿 8개 + RRF

**자유 Text2Cypher(LLM이 Cypher를 쓰는 것)는 쓰지 않는다.** 최고 모델도 실행 정확도 60~77%이고 시간 조건·집계에서 더 낮으며, 실행은 되지만 틀린 질의가 그럴듯한 오답을 낸다(phase4-research 1.4). 템플릿은 사람이 검증한 질의이므로 질의 자체는 틀리지 않는다.

| 템플릿 | 하는 일 | 깊이 | 쓰는 질문 |
|---|---|---|---|
| T1 `holder_chain` | 최대주주를 따라 위로 | ≤3 | g01·g02·g03 |
| T2 `descendants` | 출자를 따라 아래로, 경로별 지분율 곱(파생) | ≤3 | g02·g04·g05·g06 |
| T3 `ownership_path` | 두 회사 사이 지분 경로 | ≤3 | (질문 5 변형용. 12개 중엔 없음 — 평가에서 쓰이지 않으면 뺀다) |
| T4 `shared_positions` | 같은 시점에 두 회사 이상에서 임원인 사람 | 2 | g10·g11 |
| T5 `person_history` | 한 사람의 임원 이력 시간순, 연속 보고서는 기간으로 합침(파생) | 1 | g12 |
| T6 `corp_lineage` | 이름 목록 + `FORMERLY` | ≤2 | g07·g08·g09 |
| T7 `facts_at` | 한 회사의 그 시점 최대주주·임원 (1-hop) | 1 | g03·g08 |
| T8 `evidence_chunks` | 결과 행의 `source_rcept_no` → Document → 그 섹션의 Chunk | 2 | 모든 템플릿 뒤에 붙음 |

- **시점 필터는 Cypher 조각 하나를 상수로** 두고 모든 템플릿이 재사용한다: `r.valid_from <= $as_of AND (r.valid_to IS NULL OR r.valid_to > $as_of) AND r.superseded_by IS NULL` (`src/loaders/as_of.py`의 `AS_OF_FILTER`와 같은 뜻).
- **라우터:** ① 규칙(단어 패턴: "최대주주의 최대주주", "손자회사", "겸", "옛 이름" …)으로 템플릿을 고른다 → ② 못 고르면 LLM에게 "템플릿 1~8 중 몇 번인가, 없으면 0"만 묻는다(고르기만, 질의는 쓰지 않음) → ③ 0이면 그래프 없이 Phase 3 검색만.
- **빈칸 채우기:** 회사·사람 이름은 DuckDB에서 만든 사전(`target_corp`·`corp`·공시에 나온 이름·`person`)으로 corp_code·person_id를 찾는다. Phase 1의 이름 연결 규칙(`resolve`)을 그대로 쓰고, 후보가 여럿이면 추측하지 않고 되묻는다. 날짜는 "2024년 말" → `2024-12-31`처럼 규칙으로.
- **합치기:** 그래프 결과 행과 공시 글 검색(Phase 3 하이브리드) 결과를 RRF(k=60)로 섞는다. 크로스인코더 재순위는 하지 않는다(phase4-research 1.5, 0009에서 hit@5를 낮춤).
- **LLM에 넘기는 형태:** 관계 표(출발, 관계, 도착, 값, `valid_from`, `valid_to`, 근거 접수번호) + 그 공시의 조각. 유효 기간을 사실 바로 옆에 둔다. 예산은 phase4-research 3절 5번(관계 행 ≤50, 총 약 12k 토큰).
- **실행 기록:** API 응답에 템플릿 이름·채운 빈칸·행 수를 함께 돌려준다. 답이 틀렸을 때 라우터 잘못인지, 템플릿 잘못인지, 데이터 잘못인지 바로 보인다.
- 템플릿 밖의 그래프 질문은 "지금 답할 수 없는 질문"이라고 답한다. 억지로 비슷한 템플릿을 쓰지 않는다.

## 대안 비교

| 대안 | 판단 | 이유 |
|---|---|---|
| LLM이 Cypher를 쓰게 함(Text2Cypher) | 제외 | 실행 정확도 60~77%, 시간·집계에서 더 낮음(1.4). 우리 질문 12개는 템플릿 7개로 덮인다 |
| LLM이 원문에서 관계를 뽑아 그래프에 넣음(GraphRAG·LightRAG식, ETH "약한 노드") | 제외 | 공시 QA에서 Pass 42.5%·13.7%(2.4), 약한 노드 관계 F1 0.571(2.2). 우리 관계는 이미 정형 API로 정확하게 있다 |
| `neo4j-graphrag` 패키지 | 제외 | RRF 없음, 하이브리드에 필터 없음, 한국어 분석기(0004) 설정 불가(4절). 드라이버 + 직접 Cypher가 이미 있다. "인덱스 hit → 그래프 확장 → 속성만 반환" 구조만 가져온다 |
| PCST·PPR 같은 그래프 알고리즘 탐색 | 보류 | 회사 59곳·사람 수백 명 규모에서 1~3단계 고정 탐색으로 충분(3절). 평가에서 1-hop이 모자랄 때만 다시 본다 |
| 크로스인코더 재순위 | 제외 | 다리 문서를 떨어뜨린 사례(1.5), 우리 0009에서도 hit@5 하락 |

## FIBO 대응표 (참고 어휘)

FIBO는 그래프 형식으로 쓰지 않고 이름 대응만 적는다(phase3-research 5절). 용어는 phase3-research에서 확인한 것만.

| 우리 | FIBO | 비고 |
|---|---|---|
| `OWNS` | `owns` / `isOwnedBy`, 주주는 `hasOwningParty` | FIBO도 소유에 시작·종료 시점과 지분율을 단다 |
| 지배 판정(파생) | `hasControllingParty` | 지배 = 직접·간접으로 경영을 지시할 권한. 우리는 판정을 저장하지 않는다 |
| `HOLDS_POSITION` | 대응 없음으로 둠 | FIBO의 역할(role) 모델은 확인하지 않았다. 확인 전에는 적지 않는다 |
| `FORMERLY`, 사외이사 구분 | 대응 없음 | 한국 공시 고유 개념 |

## 평가 (측정 전이라 예상치는 적지 않는다)

- 질문 12개로 **검색만(Phase 3) / 그래프만 / RRF 결합** 셋을 잰다. 지표는 근거 접수번호 hit@k(검색), 정답 일치(사람 채점).
