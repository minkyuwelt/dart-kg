# 0007. 공시 원문 XML 파서: 내장 파서 + 전처리 + lxml 복구 3단계

- 날짜: 2026-11-24
- 상태: 채택 (단계별 건수는 노트북 실측 후 아래 "검증 결과"에 추가)
- 관련: `docs/plans/phase3.md` (B) 파싱, `src/loaders/document_parser.py`

## 배경

Phase 3는 정기보고서 원문(document.xml, ZIP 안 DART 자체 XML)을 섹션 단위로 풀어야 한다. 3번 PR(#30)은 파이썬 내장
`xml.etree.ElementTree`만 썼다. 외부 라이브러리를 미리 넣을 근거("깨질지도 몰라서")가 없었기 때문이다.

2026-11-24 노트북에서 사업보고서 187건(파일 458개: 본문 + 첨부)을 돌린 결과 **436개(95%)가 실패**했다.

| 원인 | 예 | 오류 |
|---|---|---|
| 그대로의 `<` | `<P><당기말></P>` | `mismatched tag` — "당기말"을 태그로 읽고 닫는 태그가 없음 |
| 그대로의 `&` | `<TH>S&P</TH>` | `not well-formed (invalid token)` |

DART 원문은 이름만 XML이고 실제로는 HTML처럼 느슨하다. 이것이 외부 라이브러리를 넣는 근거다 (요구사항 F3: 원문 → 청크가 되어야 함).

## 후보

| 후보 | 되는가 | 글자 보존 | 의존성 | 판단 |
|---|---|---|---|---|
| 내장 ElementTree만 | ✕ 5% | — | 없음 | 단독으로는 불가 |
| **전처리(`&`→`&amp;`, 태그 아닌 `<`→`&lt;`) + 내장** | 두 원인은 해결. 닫히지 않은 태그는 못 잡음 | ◎ `<당기말>`이 글자로 남음 | 없음 | 2단계 |
| **lxml `recover=True`** | 거의 모든 파일 | ○ 모르는 태그(`<당기말>`)는 태그로 보고 글자를 버릴 수 있음 | lxml (C 확장, pip) | 3단계 (전처리 뒤에) |
| BeautifulSoup | 되지만 느림(28MB × 수백 파일). HTML 규칙이 DART 태그를 소문자로 바꾸거나 구조를 고침 | ○ | bs4 (+lxml) | 제외 |
| SAX/iterparse | 같은 파싱 오류를 똑같이 냄 | — | 없음 | 제외 (스트리밍은 깨진 파일 해결책이 아님) |
| 외부 DART 라이브러리(dart-fss 등) | 원문 ZIP 섹션 파싱 기능이 아니고 뷰어 스크래핑 | — | 개인 프로젝트 의존 | 제외 (dart_client 규칙과 충돌) |

## 결정

**세 단계를 순서대로 시도하고, 성공한 단계를 `document_parse.parser`에 기록한다.**

1. `etree`: 내장 파서 그대로
2. `etree+escape`: 엔티티가 아닌 `&`, 태그 이름이 될 수 없는 글자가 따라오는 `<`, 속성값 안의 따옴표(`ENG="" KB Insurance Co., Ltd ""`)를 엔티티로 바꾼 뒤 내장 파서
3. `lxml`: 전처리한 바이트를 lxml recover 모드로

전처리를 lxml 앞에 두는 이유는 글자 보존이다. `<당기말>`을 lxml 복구에 바로 넣으면 "당기말"이 태그 이름이 되어 본문에서 사라진다.
전처리 뒤에는 `&lt;당기말&gt;`이라 어느 파서든 글자로 읽는다. lxml은 닫히지 않은 태그처럼 전처리로 못 잡는 경우만 맡는다.

버전은 `lxml==6.1.2`로 고정한다 (6.1.3이 최신이지만 갓 나온 버전은 피한다는 기존 원칙, `docs/devlog/2026-11-23.md`).

## 함께 정한 규칙: 칸 하나짜리 표는 글상자

1차 파싱 결과에서 재무제표 주석 섹션이 모두 "문단 0, 표만 있음"이었다. 깨진 것이 아니라 DART가 주석 본문을 **칸 하나짜리 표**
안에 쓰기 때문이었다("1. 지배기업의 개요" 본문 전체가 TD 하나 안에 있었음). 칸(TD/TH)이 하나 이하인 표는 표가 아니라 문단으로 취급한다.
P가 있으면 P 단위로, 없으면 통째로 문단 하나.

## 검증 결과

- 1차 (전처리 `&`·`<`만, 2026-11-24): 458개 파일 전부 파싱. etree 22 / etree+escape 307 / lxml 129(28%).
  lxml로 간 KB 본문은 섹션 75개(제목 174개 중 100개 가까이 잃음), 주석 글자가 표로 들어감 → lxml 복구는 구조를 어긋나게 할 수 있어
  **3단계 비율이 높은 것 자체가 문제**. 2단계 실패 원인은 속성값 안 따옴표 → 전처리에 추가
- 2차 (속성 따옴표 전처리 + 글상자 규칙): 노트북 재실행 후 단계별 건수를 여기에 적는다

## 다시 판단할 조건

- 3단계(lxml)로 파싱된 파일에서 섹션·표가 눈에 띄게 빠지면 → 전처리 규칙 추가로 2단계 비율을 높인다
- 세 단계 모두 실패하는 파일이 1%를 넘으면 → 그 파일들의 원인을 따로 조사
