# 0012. 변화 리포트: 무엇을 "변화"로 보고, 어디로 보내나

날짜: 2026-11-25 · 상태: 채택 (1차 범위) · 관련: `docs/plans/usecases.md` 차별점 D4, 0005 이중 시간축

## 요구사항

사용자(분석가·기자·IR 담당)가 매주 묻는 것은 "이번 주 들어온 공시 때문에 **무엇이 바뀌었나**"다. 공시 알림 서비스는 "새 공시가 올라왔다"까지만 알려 주고 무엇이 바뀌었는지는 사람이 열어 봐야 한다. 우리는 Phase 2에서 관계 테이블(임원·최대주주·출자)을 보고서 기준일 스냅샷으로 쌓고 다음 보고서 기준일에 닫아 두었으므로(0005), 두 스냅샷의 차이가 곧 변화다. 추가 수집도 LLM도 필요 없다.

## 결정 1. 변화의 정의

이 보고서의 스냅샷(`valid_from` = 기준일, `superseded_by IS NULL`)과 **같은 회사의 직전 스냅샷**(그보다 이른 가장 늦은 기준일)을 키로 맞춰 비교한다.

| 테이블 | 키 | 변화 종류 |
|---|---|---|
| executive | `person_id` (0006) | 신규(이번에만), 퇴임(직전에만), 직위·등기 구분 변경(둘 다 있고 값이 다름) |
| major_shareholder | 주주명 + 주식 종류 | 명단 추가, 명단 제외, 기말 지분율 차이 ≥ 0.1%p |
| major_shareholder_change | — | 이 보고서가 처음 보고한 변동(변동일·원인) 전부 |
| investment | 출자 대상 이름 + 주식 종류 (취득 시점별 행은 지분율 합산) | 대상 추가, 대상 제외, 지분율 차이 ≥ 0.1%p |
| 세 테이블 공통 | `superseded_by` = 이 접수번호 | 정정 공시가 대체한 행 수 (값 비교는 2차) |

- **첫 보고서(직전 스냅샷 없음)는 변화 0건**으로 둔다. 임원 30명을 "신규"로 쏟아내는 건 변화가 아니다.
- **정정본**: 원본 행은 `superseded_by`로 닫히므로 비교는 정정본 스냅샷으로 한다. 원본 접수번호는 "정정 공시가 N행 대체"로만 나온다.
- **지분율 문턱 0.1%p**: 자사주 소각·주식 수 변동으로 소수점 둘째 자리가 흔들리는 경우를 걸러내기 위한 값. 사업보고서 시즌 리포트를 보고 조정한다(사용자 결정 2026-11-25: 0.1로 시작).
- **표가 통째로 없으면 비교하지 않는다 (2026-11-27, 첫 매일 운영 뒤):** 분기보고서는 타법인 출자 표를 싣지 않는 회사가 있어(DART가 '-' 한 행만 줌), 직전 사업보고서의 출자 전부가 "제외"로 잡혔다(하나증권 분기보고서 한 건에 5,587건). 이름이 '-'·빈 행은 자리 표시라 대상으로 세지 않고, 이번이나 직전 스냅샷에 실제 행이 없으면 그 표의 비교를 건너뛴다. 표가 없는 것은 변화가 아니라 "이 보고서에 그 표가 없음"이다. 임원·최대주주 표에는 같은 일이 아직 안 보여 출자에만 둔다.
- 사람은 이름과 직위만 적는다. 생년월은 식별(`person_id`)에만 쓰고 표시하지 않는다(0006).
- 사명 변경은 1차에서 빼지 않았다 — `disclosure.corp_name`이 바뀐 것을 보면 되지만, 회사명 기준 변화는 `corp` 테이블 갱신(Phase 1)에서 따로 봐야 해서 2차.

## 결정 2. 출력

- markdown 파일 `data/reports/changes_{끝날짜}.md` (커밋하지 않음). 회사별 → 변화 종류별 표, 각 보고서에 DART 뷰어 링크.
- 기간 기본 7일(`--days 7`). 노트북이 며칠 꺼져 있어도 놓치지 않을 만큼이고, 사업보고서 시즌(3월 중순)에는 보고서 수십 개가 한 파일에 들어간다.
- Dagster 자산 `change_report`를 `relations` 뒤에 붙여 매일 08:30 관계 재생성 다음에 자동으로 남긴다. 메타데이터에 보고서 수·변화 건수·종류별 건수를 적어 Dagster 화면에서 "오늘 변화가 있었나"를 볼 수 있다.
- 화면 표시는 FastAPI + Next.js로 간다(사용자 결정 2026-11-25, 0013에서 기록). 이 모듈은 `ReportChanges` 데이터와 markdown을 둘 다 돌려주므로 API가 JSON으로 그대로 내보낼 수 있다.

## 결정 3. 알림 수단 — 1차에서는 보내지 않는다

후보는 둘이다.

| | Python 직접 호출 | n8n |
|---|---|---|
| 방식 | 자산 끝에 텔레그램/슬랙 webhook 또는 SMTP 호출 20~30줄 | Dagster가 파일·webhook을 남기고, n8n 워크플로가 받아 메일·메신저로 전달 |
| 장점 | 의존성 없음, 테스트 쉬움, 지금 당장 됨 | 받는 사람·채널을 코드 없이 바꿀 수 있음, 바깥 서비스 연결이 많아질 때 유리 |
| 단점 | 수단이 늘면 코드가 늘고, 토큰·주소를 `.env`에 쌓게 됨 | 컨테이너 하나 더(메모리·관리), 워크플로가 저장소 밖에 있어 재현이 흐려짐 |

결정을 **미룬다**. 지금은 받는 사람이 없고(포트폴리오 단계), 보낼 곳이 정해지지 않은 채 수단을 고르면 근거가 "써 보고 싶어서"가 된다(CLAUDE.md가 금지하는 근거). 쓸 사람과 채널이 정해지면 이 절을 다시 쓴다. 그때까지 리포트는 파일과 Dagster 메타데이터로 남고, 화면(0013)에서 본다. 파이프라인 자체는 어느 쪽이든 Dagster 그대로다 — n8n은 바깥 연결용으로만 검토한다(사용자 2026-11-25).
