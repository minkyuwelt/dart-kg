# 0013. 화면과 배포: FastAPI + Vite/React, Vercel

날짜: 2026-11-25, 화면 기술 비교 2026-11-27 · 상태: 채택 · 관련: `docs/plans/usecases.md` 4절, 0012

## 결정

- **백엔드 API는 FastAPI** (`src/api/main.py`). 기존 Python 함수(`src/rag/ask`, `src/reports/changes`, `src/loaders/as_of`)를 HTTP로 감싸기만 한다. 새 로직을 API 층에 두지 않는다 — Dagster 자산이 함수를 호출만 하는 것과 같은 원칙.
- **프론트엔드는 Vite + React (SPA)**, 같은 저장소의 `web/`, **Vercel에 배포**. 처음(11-25)엔 Next.js로 적었다가 11-27에 비교하고 바꿨다(아래 "화면 기술 비교").
- Streamlit은 쓰지 않는다. 처음 계획(phase3.md 7절 11번, usecases.md)은 Streamlit 한 페이지였으나 사용자가 "실제 도구 수준의 화면, Vercel 배포"로 방향을 바꿨다(2026-11-25).

## 이유 (API·배포처는 사용자 결정이라 비교표는 쓰지 않는다)

- 사용자가 Vercel 배포를 전제로 "전문적인 화면"을 원했다. Vercel은 프론트엔드와 가벼운 서버 함수를 돌리는 곳이라 Streamlit은 올릴 수 없다. 정적 파일(Vite 빌드 결과)은 그대로 올라간다.
- DuckDB 파일·Neo4j·kure-v3 임베딩은 Vercel에 올릴 수 없으므로 어떤 화면을 고르든 API 서버가 따로 필요하다. 그 서버는 Python 함수를 그대로 감쌀 수 있는 FastAPI가 가장 짧다. 자동 생성되는 OpenAPI 문서(`/docs`)가 포트폴리오에서 "직접 호출해 보세요"로 쓰인다.

## 화면 기술 비교 (2026-11-27, 사용자 요청으로 비교)

요구사항: ① Vercel 배포(사용자 결정) ② 데이터는 전부 FastAPI에서 오므로 화면 쪽 서버 기능(SSR·DB 접근)이 필요 없고, 검색엔진 노출도 필요 없다(질문을 쳐야 내용이 생기는 도구) ③ 질문 한 페이지로 시작해 변화 리포트·회사 페이지가 붙는다(3~5페이지) ④ 혼자 유지, 포트폴리오로 보임.

| 후보 | 장점 | 단점 | ①②③④ |
|---|---|---|---|
| **Vite + React (SPA) — 채택** | 가장 단순. 정적 파일이라 Vercel에 그대로. React 지식은 Next.js와 같음. 빌드 수 초(이 환경 0.2초) | 라우팅(react-router)을 직접 넣음. "Next.js" 키워드 없음 | ◎ ◎ ○ ○ |
| Next.js (App Router) | Vercel이 만든 것이라 배포가 가장 매끄럽고 채용 공고에 가장 많이 보임 | 서버 컴포넌트·캐시 규칙 등 **쓰지 않을 기능**이 기본값에 섞여 배우고 피할 것이 많음(생성된 설정에 `cacheComponents` 등). 버전마다 규칙이 바뀜 | ◎ △ ○ ◎ |
| SvelteKit | 코드가 짧고 Vercel 어댑터 공식 | 새 문법, 국내 채용 수요 적음 | ◎ ○ ○ △ |
| Astro | 정적 콘텐츠에 강함 | 우리 화면은 전부 동적이라 강점이 안 쓰임 | ◎ △ ○ ○ |
| FastAPI + HTMX/Jinja | 프론트 저장소·빌드가 없음 | 화면이 API 서버에 붙어 Vercel에 올릴 것이 없음 → ① 충돌 | ✗ |

판단: ②가 결정적이다. Next.js의 핵심(서버 렌더링·서버 컴포넌트·캐시·서버 함수)은 화면 쪽 서버가 데이터를 직접 만질 때 가치가 있는데 우리는 그 상황이 아니고, 쓰지 않는 기능의 규칙을 배우고 피하는 비용만 남는다. Next.js를 고를 이유는 ④(채용 키워드)뿐인데, 그것은 기술 근거가 아니다(CLAUDE.md: "많이 쓰여서"는 근거가 아님). 포트폴리오에는 "왜 Next.js를 안 골랐나"를 적는 쪽이 판단을 보여 준다.

사용자가 "Vite가 오래된 기술 아니냐"고 물어 조사했다(11-27, 2차 블로그 중심이라 수치는 서로 안 맞음): 오래된 것은 Create React App이고 React 공식 문서가 SPA에 Vite를 권한다. Vite 8(2026)은 Rust 번들러(Rolldown) 기반. 2026년 가이드들은 "로그인 뒤 도구·대시보드 → Vite SPA, 공개 페이지·SEO → Next.js"로 나눈다. 비슷한 RAG 화면들은 갈려 있다(Open WebUI: Svelte, Dify·Onyx: Next.js, LibreChat: React, HF Chat UI: SvelteKit) — 서버 기능을 가진 것들은 로그인·멀티테넌트 때문이고 우리에겐 없는 요구다. 채팅 형식 화면은 프레임워크와 무관하게 어느 쪽으로도 만들 수 있다.

같이 정한 것:
- **TypeScript**: API 응답 꼴을 타입으로 적어(`web/src/api.ts`) 서버 모델과 칸 이름이 어긋나면 빌드에서 잡는다.
- **CSS는 Tailwind 없이 CSS Modules + 변수**: 페이지 3~5개에 디자인 토큰 6개뿐이라 유틸리티 프레임워크를 배울 이유가 없다. 토큰은 `web/src/index.css` 한 곳.
- **글꼴 Pretendard**(SIL OFL, CDN): 한국어 본문용 가변 글꼴. 로마자 글꼴을 쓰면 한글이 시스템 글꼴로 떨어져 두 글꼴이 섞인다.
- **린트는 Vite 템플릿의 oxlint** 그대로(별도 결정 없음). 개발 서버 포트 5173(3000·8080은 노트북의 다른 수업이 씀).
- API에 CORS(`API_CORS_ORIGINS`, 비우면 Vite 개발 서버만). CI에 `web` job(npm ci → lint → build).

## 첫 화면: 질문 한 페이지 (2026-11-27, `feat/web-ask`)

- 구성: 질문 상자(주인공) → 왼쪽 답(본문 폭 38rem) + 오른쪽 근거 공시 목록(좁은 화면은 위아래). 답의 인용 번호 [n]과 근거 n이 같은 번호이고 누르면 그리로 이동. **인용된 근거만 형광펜 띠**, 나머지는 흐리게 — 이 페이지에서 눈에 띄는 것은 이것 하나다. 그래프 질문이면 관계표(파생 값 → 관계 행 → "어떻게 찾았나" trace)가 답 아래에 붙고, 답이 관계표를 인용하면([그래프 번호]) 관계표 제목에 같은 번호가 붙는다.
- 처음 화면에는 평가 세트의 실제 질문 5개를 두어 "무엇을 물을 수 있나"를 보인다. 서버 상태(`/health`: 색인 수, LLM 키, DuckDB·Neo4j)는 오른쪽 위 한 줄.
- 화면에 새 로직을 두지 않는다. 관계 종류 코드(OWNS·HOLDS_POSITION…)를 우리말로 바꾸는 표시용 사전만 있다.
- 채팅 형식(대화가 쌓이고 이어 묻기)은 API가 이전 대화를 받지 않으므로 지금은 안 한다. "이 세션에서 물은 질문 목록"은 다음 PR 후보.

## 둘째·셋째 화면: 변화 리포트, 회사 페이지 (2026-11-27, `feat/web-changes`, `feat/web-corp-page`)

- 변화 리포트(`/changes`): 기간·회사를 고르면 보고서별로 바뀐 것만 표로. 바뀐 것만 또렷하고 나머지는 흐리게.
- 회사 페이지(`/corps/:corp_code`): 회사 하나·기준일 하나에 **지분 추이 → 최대주주 → 임원 → 지주 겸직 표의 자리 → 타법인 출자** 순서로 표 다섯. 돕는 업무 질문(usecases 2절): 1(그 시점 대표·최대주주), 6(이 자회사의 지분율·장부가액이 해마다 어떻게 변했나 — 지분 추이 표가 처음으로 답한다), 3(겸직).
  - API는 `GET /corps/{corp_code}?as_of=` 하나로 묶어 준다(`as_of.corp_page`): 화면이 요청 한 번, DuckDB도 한 번만 연다. 새 로직은 서버 쪽 SQL(출자·겸직·지분 추이 시점 함수)이고 화면은 원 단위 숫자를 억·조로 바꾸는 표시만 한다.
  - 임원 표가 없는 회사(감사보고서만 내는 KB자산운용 등)는 "정기보고서 없음"을 머리에 적고, 지주 겸직 표의 자리가 아는 전부임을 임원 칸에 적는다(0014의 닫힌 세계 범위를 화면에서도 밝힌다).
  - 회사를 안 골랐을 때는 지주 4곳과 자회사 이름 전부를 펼쳐 보인다(59개는 고르는 상자보다 한눈에 들어온다). 출자 대상·최대주주·지주 이름이 수집 대상이면 그 회사 페이지로 이어진다.
  - 표 행의 근거 칸은 접수일(접수번호 앞 8자리)만 보이고 누르면 DART 뷰어. 생년월·person_id는 서버가 내보내지 않는다.

## 둘째 다듬기: 서류철 꼴 (2026-11-27, `feat/web-corp-page`)

사용자 평가 "화면이 너무 보기 힘들다, 페이지가 길어서 눈에 안 들어온다"에서. 첫 꼴(흰 종이에 괘선만)은 글·표·제목이 전부 같은 회색 14px이고 괘선 하나로만 나뉘어 **덩어리가 안 보였다**.
- 꼴: **연회색 책상 위의 흰 서류**. 바탕 `--desk`, 내용 덩어리마다 흰 판(`.panel`, 테두리 1px, 모서리 8px, 그림자 없음). 판 하나 = 표 하나. 판 머리에 제목·건수·한 줄 설명.
- 색 다섯 그대로, 파랑만 공시 남색(`#0f3d91`)으로 짙게 해 링크·현재 탭·단추가 회색 글과 또렷이 갈린다. 형광펜은 인용 근거에만. 그라데이션·그림자·움직임 없음(생성된 화면의 흔한 꼴을 피하려는 것이기도 하다).
- 글자: Pretendard 하나, 굵기로만. 본문 16, 표 15, 회사 이름 28. 표 머리 행은 회색 면, 본문 행 44px, 첫 열 굵게, 숫자 오른쪽. 근거는 접수일 칩(누르면 DART).
- 공통 부품(`.panel`·`.tbl`·`.chip`·`.btn`·`.field`)은 `index.css`에 전역으로 둔다 — 세 페이지가 같은 표를 쓰는데 CSS 모듈마다 반복하면 서로 어긋난다. 페이지 모듈에는 그 페이지만의 배치만.
- 긴 페이지: 회사 머리 판에 **표 바로가기(이름 + 건수, 0건은 흐리게)**, 표는 처음 8줄만 보이고 "나머지 N줄 더 보기", 지분 추이는 12월 말 행만 기본(분기는 단추). 변화 리포트는 보고서 한 줄씩 접힘 그대로. 질문 페이지는 근거 판이 따라오는(sticky) 그대로.
- 그림은 데이터에서만(사용자 "텍스트뿐이라 밋밋하다"): ① 회사 머리 판의 **지배구조 그림**(지주 → 이 회사 → 출자 회사 6곳, 선 위에 지분율, HTML 상자 + CSS 선이라 좁은 화면에서 세로로) ② 지분 추이 장부가액 칸의 얇은 막대(같은 표의 최댓값 기준, 한 색) ③ 질문 시작 화면의 **지주 지도**(지주 4칸에 자회사 칩) ④ 남색 마크·파비콘. Vite 템플릿이 남긴 보라색 그림(hero.png·icons.svg·vite.svg)은 지움. 사진·일러스트·회사 로고(상표)는 쓰지 않는다.
- 설명 글은 최소로(사용자 "불필요한 설명 없애자"): 판 머리의 설명은 출처가 헷갈리는 겸직 표 자리에만, 고르는 줄의 안내문과 긴 빈 상태 문장은 뺌.
- 확인: 가짜 API 응답으로 1280·390px 화면을 찍어 표가 글자 단위로 꺾이지 않는지(표 최소 너비 640px, 판 안에서 가로 스크롤) 봤다.

## 넷째 화면: 질문 이력 (2026-11-27, `feat/web-history`)

- 물은 질문과 그 응답을 **브라우저(localStorage)에만** 최근 50개. 서버에 쓰려면 API가 DuckDB에 써야 하는데 API는 읽기 전용 연결이고(Dagster 잠금 규칙), 혼자 쓰는 도구에 새 저장소를 둘 이유가 없다. 다른 기기·브라우저에는 없다는 뜻이고, 그렇게 화면에 적는다.

## API 설계에서 지킨 것

- **DuckDB는 요청마다 읽기 전용으로 열고 바로 닫는다.** 서버가 연결을 쥐고 있으면 Dagster의 매일 쓰기가 막힌다(CLAUDE.md 잠금 규칙). 잠금에 걸리면 503으로 "잠시 뒤 다시".
- **임베딩 모델(2GB)·Neo4j 드라이버는 서버 시작 때 한 번** 열어 둔다(lifespan). 요청마다 열면 질문 하나에 몇십 초가 든다.
- LLM 클라이언트는 요청마다 만든다. 키가 없으면 503과 함께 이유를 돌려준다. `use_llm=false`면 검색만 하므로 키 없이도 동작한다.
- 임원 응답에 생년월·`person_id`를 넣지 않는다(0006). 모든 근거 행에 DART 뷰어 링크를 붙인다(D3).
- 응답 설명에 "수치는 공시 그대로, 투자 판단용이 아니다"를 적는다(usecases 질문 11 원칙).

## 키: 공개 서버에 운영자 키를 두지 않는다 (2026-11-27, `chore/vercel-prep`)

사용자 질문 "배포하면 내 OpenAI 키가 쓰이나 / 아예 못 쓰게 할 수 없나". 답: **공개 서버의 `.env`에 `OPENAI_API_KEY`를 두지 않는다.** 그러면 내 키는 어디에도 없다. 대신 보는 사람이 자기 키를 넣는다.
- 화면: 서버 `/health`의 `llm_key`가 false면 질문 상자에 "OpenAI 키" 칸이 보인다. 키는 **그 브라우저의 localStorage에만** 두고(`web/src/key.ts`), `/ask` 요청 헤더 `X-OpenAI-Key`로만 보낸다. Vercel에는 가지 않는다(정적 파일뿐). `VITE_` 환경변수는 빌드에 박혀 공개되므로 키를 거기 넣지 않는다.
- 서버: 헤더 키가 있으면 그 요청의 답변 LLM·템플릿 고르기 LLM에만 쓰고 저장·기록하지 않는다. 없으면 `.env` 키(노트북), 둘 다 없으면 503과 안내. 키가 틀리면 401. CORS가 이 헤더를 허용한다.
- 키 없이도 되는 것: 근거 공시 검색, 규칙이 고른 그래프 질문의 관계표, 변화 리포트, 회사 페이지. 안 되는 것: 문장 답, 규칙이 못 고른 질문의 템플릿 고르기.
- 대안으로 본 것: 서버에 내 키 + 비밀 토큰·하루 상한 — 토큰이 새면 내 비용이고, 혼자 쓰는 도구에 상한 관리까지 두는 건 과함. 키를 아예 두지 않는 쪽이 단순하고 확실하다.

## 배포할 때 확인할 것 (노트북에서 먼저 잰다)

| 항목 | 왜 | 어떻게 | 측정(2026-11-27, 노트북 WSL, `API_EMBED_DEVICE=cpu`) |
|---|---|---|---|
| 질문 임베딩 시간, GPU 없는 서버 | kure-v3는 1.1B 모델. CPU면 질문 1건에 1~2초로 어림 | `API_EMBED_DEVICE=cpu uvicorn …` 뒤 `/ask` 5번(`use_llm:false`)의 응답 시간 | 2.86 / 1.05 / 0.94 / 0.54 / 0.47초. 첫 질문만 예열로 느리고 이후 1초 안 |
| 메모리 | 모델 + Neo4j 드라이버 + FastAPI | `uvicorn` 프로세스 RSS | **2,709 MB** (bf16으로 올라간 상태) |
| Neo4j·DuckDB를 어디에 두나 | 배포 서버에 Docker(Neo4j)와 DuckDB 파일을 함께 올려야 한다. 재생성은 코드로 가능(CLAUDE.md 원칙) | — | 아래 결정대로 노트북에 그대로 둔다 |
| CORS | Vercel 도메인에서 API를 부른다 | `.env`의 `API_CORS_ORIGINS` | 터널 주소가 아니라 **Vercel 주소**를 적는다(브라우저가 보는 출처는 화면 쪽) |

속도는 문제가 아니고 **메모리 2.7GB가 결정 요인**이다. 무료 서버(Render·Fly·Railway 등 512MB~1GB)에는 올라가지 않고, Neo4j까지 같이 두면 4GB급 VM이 필요하다.

## API 서버를 어디에 두나: 노트북 + 터널 (2026-11-27, `docs/deploy-tunnel`)

배포 목적은 포트폴리오에 "공개 배포를 해 봤다"고 적을 수 있을 만큼의 **시연 가능한 공개 주소**다. 상시 서비스가 아니다. 과정이 끝나면 노트북을 반납한다.

| 안 | 비용 | 코드 변경 | 문제 |
|---|---|---|---|
| 1. 4GB급 유료 VM 1대 (Hetzner·Fly 등, 월 5~8천 원대) | 있음, 반납 뒤에도 계속 | 없음 (Docker로 Neo4j + uvicorn) | 혼자 시연하는 용도에 상시 요금. DuckDB·Neo4j 데이터(수 GB)를 옮겨야 함 |
| **2. 노트북에서 uvicorn을 돌리고 터널로 공개** | 0원 | 없음 | 노트북이 켜져 있을 때만 열림. 반납하면 끝 |
| 3. 임베딩을 OpenAI 임베딩 API로 바꿔 서버를 가볍게 | 무료 서버 가능 | 큼: 조각 전체 재임베딩, 검색 평가(0010) 다시 | **학원에서 받은 OpenAI 키가 서버에 있어야 함** → "공개 서버에 운영자 키를 두지 않는다"(위 절)와 충돌 |

**2번.** 목적(시연)에 맞고, 돈이 들지 않고, 키 원칙을 지킨다. 나중에 정말 상시 공개가 필요해지면 1번으로 바꾸되 코드는 같다.

터널 도구는 **Cloudflare Tunnel의 빠른 터널(quick tunnel)** 을 쓴다: 계정·도메인 없이 `cloudflared tunnel --url http://localhost:8000` 한 줄로 `https://….trycloudflare.com` 주소가 나오고, 브라우저 경고 페이지가 없다(ngrok 무료는 fetch 요청에도 경고 페이지가 끼어 헤더 처리가 더 필요하다). 단점은 **켤 때마다 주소가 바뀐다** → Vercel의 `VITE_API_URL`을 고쳐 다시 배포해야 한다(1~2분). 시연 기간에 터널을 계속 켜 두면 한 번으로 끝난다. 주소가 바뀌는 게 번거로워지면 Tailscale Funnel(무료, 고정 주소, 계정 필요)이나 Cloudflare 이름 있는 터널(도메인 필요)로 바꾼다.

절차는 README "Vercel에 올리기"에 적었다. 공개하는 동안 노트북 `.env`에서 `OPENAI_API_KEY`는 비워 둔다(보는 사람은 자기 키를 넣는다) — 키 절의 원칙을 노트북 서버에도 그대로 적용한다. 시연이 끝나면 터널을 끄고 키를 다시 채운다.
