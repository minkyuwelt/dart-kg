## 1. 이 단계가 끝나면 할 수 있어야 하는 것

터미널에서 질문 하나를 넣으면, **공시 원문에서 찾은 근거 조각과 그 접수번호(`rcept_no`)를 붙여 답**이 나온다.

```bash
python -m src.rag.ask "2023년 신한은행 사외이사는 누구이고 임기는 언제까지인가"
```

```
답: ... (근거 1, 2)
근거 1: 신한은행 사업보고서 (2023.12) rcept_no 20240318000xxx, 'VIII. 임원 및 직원 등에 관한 사항 > 1. 임원 현황' 중
  "... 사외이사 ... 2022.03.24 ~ 2024.03 ..."
  https://dart.fss.or.kr/dsaf001/main.do?rcpNo=20240318000xxx
근거 2: ...
```

세 가지가 모두 되어야 끝이다.

1. **원문이 들어와 있다.** 정기보고서 618개의 원문이 노트북에 저장되고, 섹션 단위로 잘려 DuckDB에 있다
2. **찾을 수 있다.** 평가 세트 질문의 80% 이상에서, 상위 5개 조각 안에 정답 근거 공시가 들어 있다 (측정 지표는 5절)
3. **답에 근거가 붙는다.** 답의 모든 사실 문장이 조각에서 나온 것이고, 조각에 없는 내용은 "공시에서 찾지 못함"이라고 말한다

Phase 4(그래프 적재·GraphRAG)는 여기 포함하지 않는다. 다만 Phase 3의 Neo4j 노드 설계는 Phase 4가 이어 쓸 수 있게 `Document`·`Chunk` 노드에 `corp_code`를 붙여 둔다.

## 2. 처리 흐름

```
 (A) 원문 수집          document.xml (rcept_no 1건 = 호출 1건) → ZIP 파일 → data/documents/{rcept_no}.zip
         │                 DuckDB document 테이블: rcept_no, 파일 크기, 해시, 받은 시각
         ▼
 (B) 파싱·청킹          ZIP 안 XML → 섹션 트리(제목 계층) → 조각(chunk)
         │                 DuckDB document_section, chunk 테이블   ← API 호출 없이 언제든 재생성
         ▼
 (C) 임베딩             chunk.text → 벡터 (모델은 0009에서 결정)
         │                 DuckDB chunk_embedding (model_name, dim, vector)   ← 비싸므로 따로 보관
         ▼
 (D) Neo4j 색인         Document·Chunk 노드, 벡터 인덱스 + cjk 전문검색 인덱스 (0004)
         │                 ← DuckDB에서 언제든 재생성 (0001 원칙)
         ▼
 (E) 질의               질문 → 벡터 검색 + 전문검색 → 순위 합치기(RRF) → 상위 k 조각 → LLM → 근거 붙은 답
```

**단계를 이렇게 자르는 이유**는 Phase 1·2와 같다. "다시 만들 수 있는가"와 "다시 만드는 비용"이다.

| 단계 | 다시 만드는 비용 | 그래서 |
|---|---|---|
| (A) 원문 | API 618건 (하루 한도의 3%) | 받은 ZIP을 그대로 지킨다. 파싱이 바뀌어도 다시 받지 않는다 |
| (B) 청킹 | CPU 몇 분 | 규칙을 고치면 통째로 다시 만든다 (Phase 2 `relations rebuild`와 같은 방식) |
| (C) 임베딩 | 노트북 CPU면 몇 시간, API면 돈 | 청킹이 바뀌지 않은 조각은 다시 임베딩하지 않는다. 조각 본문 해시로 판단 |
| (D) Neo4j | 몇 분 | DuckDB에서 재생성. 컨테이너를 지워도 된다 |

## 3. 단계별 할 일

### (A) 원문 수집

- **API:** `document.xml` (공시서류원본파일). 파라미터 `rcept_no`. 응답은 ZIP이고 안에 DART 자체 XML이 들어 있다. `corpCode.xml`과 같은 ZIP 응답이므로 `dart_client.get_raw`를 쓴다
- **대상:** `disclosure` 테이블에서 정기보고서(`report_nm LIKE '%보고서 (%'`)로 뽑는다. Phase 2와 같은 선별 함수(`periodic_report_key`)를 재사용한다. 2021~2026년 618개
- **저장:** ZIP 파일은 `data/documents/{rcept_no}.zip`에 그대로 두고(바이너리를 DuckDB JSON 컬럼에 넣을 수 없음), `document` 테이블에 메타데이터만 적는다. 정정본(`[기재정정]`)은 접수번호가 다르므로 따로 받는다
- **Dagster:** `documents` 자산, 파티션은 `report_details`와 같은 회사 × 보고서. 백필은 `backfill_reports`처럼 프로세스 하나에서 도는 스크립트(`--dry-run` 포함)
- **매일:** `daily_report_details`(07:30)가 새 정기보고서를 찾으면 같은 보고서의 원문도 받는다

### (B) 파싱·청킹 → 결정 0008

DART 원문 XML은 HTML에 가까운 자체 형식이다. 제목 태그(`TITLE`)로 "I. 회사의 개요 > 1. 회사의 개요" 같은 계층이 있고, 본문은 문단(`P`)과 표(`TABLE`)다. 표가 많다(임원 현황, 최대주주, 출자 현황이 모두 표).

**결정할 것 (0008-chunking):**

| 질문 | 후보 | 판단 기준 |
|---|---|---|
| 조각 단위 | ① 섹션 무시, 512토큰 고정 분할(기본선) ② 섹션 단위, 긴 섹션만 길이로 나누고 앞뒤 조금 겹침, 표는 쪼개지 않음 ③ ②에 제목 경로를 조각 앞에 붙임 | 평가 세트에서 상위 5개 안에 정답이 드는 비율. 조각이 크면 찾기는 쉽지만 LLM에 넣는 양이 늘고, 작으면 문맥이 끊긴다. 의미 기반 청킹과 문단 단위는 조사 결과(조각이 너무 짧아짐)로 제외 → `phase3-research.md` 1절 |
| 표 처리 | ① 표를 통째로 텍스트로 ② 행마다 "열이름: 값"으로 풀어 쓰기 ③ 표는 빼고 Phase 2 정형 데이터에 맡기기 | "사외이사 임기" 같은 질문은 표 안에 답이 있다. ③은 Phase 2가 이미 가진 표(임원·최대주주·출자)에만 적용 가능 |
| 조각에 붙이는 정보 | 회사명, 보고서명, 섹션 경로("VIII > 1. 임원 현황"), 기준일(stlm_dt) | 임베딩 본문에 섹션 경로를 앞에 붙이면 짧은 조각도 문맥을 가진다. 실험으로 확인 |

**구현:** `src/loaders/documents.py`. 테이블 `document_section`(rcept_no, section_id, 경로, 순서, 본문)과 `chunk`(chunk_id, rcept_no, section_id, 순서, 본문, 토큰 수, 본문 해시). 모두 ZIP에서 재생성.

**인코딩 주의:** DART XML이 EUC-KR인지 UTF-8인지는 노트북에서 실제 파일을 열어 봐야 안다. 파싱 함수는 XML 선언의 encoding을 읽고, 없으면 두 가지를 순서대로 시도한다.

### (C) 임베딩 → 결정 0009

**결정할 것 (0009-embedding):** 어떤 모델로, 어디서(노트북 CPU / API) 임베딩하는가.

| 후보 | 종류 | 차원 | 장점 | 걱정되는 점 |
|---|---|---|---|---|
| **`nlpai-lab/KURE-v3`** (2026-10) | 로컬 (단일 벡터, 1.1B) | 2048 → 1024로 잘라 사용 (성능 99% 유지) | MTEB(kor,v2) 검색 nDCG@10 0.8027로 단일 벡터 모델 중 최고. 8,192토큰. MIT. 재임베딩 0원(C2) | 1.1B라 VRAM 4GB 이상 필요(확인 필요). 조각 1,000개당 시간 실측 |
| `nlpai-lab/KURE-v1` (2024-12) | 로컬 (bge-m3를 한국어로 미세조정, 568M) | 1024 | 0.7616. 작고 검증됨 | v3보다 낮음. v3가 노트북에서 안 돌 때의 대안 |
| `BAAI/bge-m3` | 로컬 (다국어, 568M) | 1024 | 0.7509. 긴 입력(8192) 가능 | 다국어 기준선. 한국어 점수는 KURE 둘보다 낮음 |
| 임베딩 API (OpenAI `text-embedding-3-small/large` 등) | 서버 | 1536/3072 | 노트북 성능과 무관. 빠름. OpenAI 키는 생성 LLM용으로 이미 있어 추가 발급이 없음 | 유료. 재임베딩마다 비용(C2와 충돌). 공시 본문을 외부에 보냄. 한국어 금융 텍스트 점수는 같은 평가 세트로 비교해야 함 |

제외한 것: KURE-v2(점수는 가장 높지만 다중 벡터라 Neo4j 벡터 인덱스에 못 올림), KoE5·multilingual-e5-large(입력 512토큰, 점수 낮음), Qwen3-Embedding-8B(노트북 GPU에 무리). 근거와 숫자는 `phase3-research.md` 2절.

**판단 기준(요구사항 인용):**
- F3·F5: 평가 세트 재현율(상위 5개 안 정답 비율)
- C1: 노트북 GPU로 조각 전체를 임베딩하는 데 걸리는 시간. 하루 밤 안에 끝나야 한다. GPU가 있으므로(2026-11-24 확인) 로컬 모델이 유력하지만, VRAM이 모델(KURE-v3 1.1B는 약 2.2GB + 배치)을 담지 못하면 v1(568M)로 내려간다
- C2: 노트북을 반납하고 다시 만들 때 드는 비용. 로컬 모델은 0원, API는 재임베딩 비용
- N1: 조각 수. 2026-11-24 사업보고서 188건 파싱 실측(본문+첨부): ZIP당 섹션 80·표 1,150·글자 27만. 글자를 1,000자 조각으로 자르면 사업보고서만 **약 5만 글 조각**, 표를 하나씩 조각으로 만들면 **약 21만 표 조각**이 더해진다. 표가 조각 수를 결정하므로 0008에서 표를 섹션 단위로 묶는지, 당기·전기 쌍을 합치는지가 핵심 변수다. 분기·반기(430건)는 사업보고서보다 작다

**실험 방법:** 사업보고서 30개(지주 4 + 자회사, 2023년)만 먼저 청킹·임베딩하고, 평가 세트 중 그 보고서에 답이 있는 질문으로 후보를 같은 조건에서 비교한다. 시간도 함께 잰다(조각 1,000개당 초). 이 실험이 0009의 근거가 된다. 일반 리더보드 순위를 그대로 믿지 않는 이유는 한국어 금융 텍스트에서는 순위가 바뀐다는 보고(TWICE, ICLR 2025)가 있기 때문이다.

**저장:** `chunk_embedding`(chunk_id, model_name, vector FLOAT[]). 모델을 바꾸면 행이 추가되고 옛 행은 남는다. Neo4j에는 채택한 모델 하나만 올린다.

### (D) Neo4j 띄우기와 색인

- **docker-compose:** `neo4j:2026.06.0-community` (0004 실험과 같은 버전 고정). 노트북 쪽 포트는 `.env`의 `NEO4J_HTTP_PORT`·`NEO4J_BOLT_PORT`로 바꿀 수 있게 (7474·7687은 다른 수업이 쓴다, C1). 비밀번호는 `.env`의 `NEO4J_PASSWORD`. `.env.example` 갱신
- **노드:** `(:Document {rcept_no, corp_code, report_nm, stlm_dt})`, `(:Chunk {chunk_id, text, text_ft, section_path, seq, embedding})`, `(:Document)-[:HAS_CHUNK]->(:Chunk)`. `corp_code`를 붙여 두는 이유는 Phase 4에서 `(:Corp)` 노드와 바로 이을 수 있게 하기 위해서다
- **인덱스:** 벡터 인덱스(차원은 0009 결정값, 코사인), 전문검색 인덱스는 `cjk` 분석기로 `text_ft` 속성에. `text_ft`는 0004의 경계 전처리(가운뎃점 → 공백, 영문·숫자와 한글 사이 공백)를 거친 본문이다. **색인과 검색이 같은 함수를 쓰도록** 전처리 함수를 `src/graph/text_normalize.py`로 옮기고, 0004의 실험 스크립트도 그 함수를 import하게 바꾼다
- **적재:** `src/graph/load_chunks.py`. DuckDB에서 읽어 `MERGE`로 넣는다(멱등). 전체 재생성은 노드를 지우고 다시 넣는다
- **0004 재확인:** 실제 원문으로 전문검색 정밀도를 다시 잰다(0004의 "한계"에 적어 둔 일). 결과를 0004에 덧붙인다

### (E) 검색·생성 → 결정 0010

**검색:** 벡터 상위 20 + 전문검색 상위 20을 RRF(Reciprocal Rank Fusion, 두 순위를 점수로 합치는 간단한 공식)로 합쳐 상위 k(기본 5)를 고른다. `neo4j-graphrag` 패키지(1.24, 2026-11)의 `HybridRetriever`가 이 패턴을 제공하지만, 전처리 함수를 검색어에 끼워 넣어야 하므로 **처음에는 Cypher를 직접 쓴다.** 패키지는 Phase 4(VectorCypherRetriever)에서 다시 검토한다.

**재순위(선택):** 하이브리드 상위 20~50개를 교차 인코더(`KURE-Reranker-nano`, 149M)로 다시 매겨 상위 5개를 고른다. 텍스트+표 문서 벤치마크에서 하이브리드 위에 재순위를 얹는 것이 단일 개선으로 가장 컸다(nDCG@10 0.551 → 0.683, `phase3-research.md` 3절). 질문당 지연과 hit@5 변화를 6번 PR 실험에 "재순위 없음 / nano" 변수로 넣어 잰다.

**필터:** 질문에 회사·연도가 있으면 `corp_code`·`stlm_dt`로 후보를 좁힌다. 1차에서는 CLI 옵션(`--corp`, `--year`)으로 받고, 질문에서 자동으로 뽑는 것은 평가 결과를 본 뒤 정한다.

**생성 (0010-llm):** OpenAI API의 `gpt-6-luna`를 쓴다 (사용자 결정, 2026-11-24). 처음에는 `gpt-4o-mini`를 생각했지만, OpenAI가 `gpt-4o-mini`를 2027-01-14에 API에서 내리면서 **후속으로 지정한 모델이 `gpt-6-luna`**이고, 가격도 더 낮다(2026-11 기준 입력 $0.10 / 출력 $0.50 per 1M 토큰, `gpt-4o-mini`는 $0.15 / $0.60). 종료 예정 모델로 시작할 이유가 없다. 평가 세트 전체를 돌리는 비용은 실측해 0010에 적는다. API 키는 `.env`의 `OPENAI_API_KEY`(`.env.example` 갱신), 패키지는 `openai`. 답은 구조화 출력(JSON 스키마: 답 본문, 인용 번호 목록)으로 받는다. **`gpt-6-luna`가 JSON 스키마 구조화 출력을 지원하는지는 9번 PR에서 호출 1건으로 확인한다.**

> 모델은 언젠가 또 바뀐다. 그래서 생성 함수는 **"조각 목록 + 질문 → 답 + 인용 번호" 인터페이스 하나로 감싸고 모델 이름은 `.env`(`LLM_MODEL`, 기본 `gpt-6-luna`)에서 읽는다.** 모델을 바꾸는 일이 환경변수 한 줄로 끝나야 한다.

**프롬프트 규칙:** 조각마다 번호와 rcept_no를 붙여 넣고, 답에는 문장마다 번호를 인용하게 한다. 조각에 없는 내용은 "공시에서 찾지 못했습니다"라고 쓰게 한다. 출력은 구조화 출력(답 본문, 인용 번호 목록)으로 받아 프로그램이 rcept_no와 링크를 붙인다.

**CLI:** `python -m src.rag.ask "질문" [--corp 00688996] [--year 2023] [--k 5] [--no-llm]`. `--no-llm`은 검색 결과만 보여 준다(평가와 디버깅용).

### (F) Dagster 자산

```
report_details ─▶ documents ─▶ chunks ─▶ chunk_embeddings ─▶ neo4j_chunks
```

- `documents`: 회사 × 보고서 파티션, ZIP 저장 (API)
- `chunks`: 파티션 없음, 전체 재생성 (API 없음)
- `chunk_embeddings`: 파티션 없음, 해시가 바뀐 조각만 임베딩 (API 없음 또는 임베딩 API)
- `neo4j_chunks`: 파티션 없음, 전체 재생성. **Neo4j가 꺼져 있으면 실패하고 다음 날 다시 시도**(노트북에서 Docker가 항상 떠 있지 않다)
- 품질 검사: 원문 없는 정기보고서 수, 조각 본문 비어 있음 0건, 임베딩 없는 조각 0건, Neo4j 조각 수 = DuckDB 조각 수
- 스케줄: `daily_documents` 08:00(그날 새 정기보고서 원문), `daily_rag_index` 09:00(chunks → embeddings → neo4j). 스케줄은 DuckDB를 열지 않는다(기존 규칙)

## 4. 평가 세트 (처음부터 만든다)

임베딩 모델도, 청킹 방식도, 프롬프트도 **이 세트의 점수로 비교**한다. 세트가 없으면 "느낌상 좋아졌다"밖에 말할 수 없다.

- **파일:** `eval/questions.jsonl`. 한 줄에 질문 하나
  ```json
  {"id": "q001", "question": "2023년 3월 31일 기준 신한은행의 최대주주는?", "type": "시점-정형",
   "answer": "신한금융지주회사 100%", "evidence_rcept_no": ["2023xxxxxxxxxx"],
   "evidence_hint": "VII. 주주에 관한 사항 > 최대주주 및 특수관계인의 주식소유 현황", "source": "phase2-Q1"}
  ```
- **크기:** 1차 30개, 2차 50개. Phase 2의 질문 5개가 씨앗이다(정답을 이미 정형 데이터로 확인했으므로 "정답이 확실한 질문")
- **유형을 섞는다:** 정형 표에 답이 있는 것(임원·최대주주·출자), 서술에 답이 있는 것(사업 개요, 위험 요인, 배당 정책), 시점이 있는 것(연도 지정), 공시에 없는 것(모른다고 해야 정답인 질문 3~5개)
- **정답 적는 법:** 질문을 만들 때 **DART 뷰어에서 해당 보고서를 직접 열어** 근거 섹션을 확인하고 rcept_no를 적는다. 추측으로 적지 않는다. 이 작업은 사람(사용자)이 한다. 질문 30개면 2~3시간
- **지표:**
  - 검색: `hit@5` (상위 5개 조각 중 정답 rcept_no의 조각이 있는 비율), `MRR` (정답이 몇 번째에 나오는지의 평균)
  - 답변: 1차는 사람이 채점(맞음/부분/틀림/근거 없는 주장 있음). LLM 채점은 사람 채점과 일치율을 확인한 뒤에만 도입
- **스크립트:** `python -m eval.run --retrieval-only` (API 호출 없이 검색만 측정), `python -m eval.run` (LLM까지). 결과는 `eval/results/{날짜}_{설정}.json`으로 남겨 설정끼리 비교
- **현재 상태 (2026-11-24):** ready 36개 (정형표 14 · 시점 10 · 서술 7 · 없음 5), draft 1개(d031 제주은행 배당: 파서 빈 칸 문제로 당기 값 미확인). 후보 107개 중 36개를 `eval.review`로 확인했고 나머지 70개는 초안 파일에 남아 있어 언제든 이어서 채울 수 있다. 타법인출자 질문 3개(d021·d024·d032)는 표 열이 밀려 정답을 가릴 수 없어 지움 → 파서 수정 뒤 지주 보고서로 다시 만든다
- **키워드 기본선 (2026-11-24, 검색 대상 32개):** hit@5 공시 0.28 / 섹션 0.19, MRR 공시 0.20 / 섹션 0.13. 유형별 hit@5 공시: 서술 0.43, 정형표 0.33, 시점 0.10. 낮은 이유는 단어 일치만 보는 검색기가 "대표이사"·"주당 현금배당금"처럼 모든 회사 보고서에 똑같이 나오는 말로는 **어느 회사의 보고서인지 가리지 못하기** 때문(회사명은 자기 보고서보다 모회사 보고서에 더 자주 나온다). 이것이 5~6번 PR에서 회사 필터(corp_code)·임베딩·재순위를 넣을 때 비교할 출발선이다. 결과 파일 `eval/results/20261124_1541_keyword_baseline.json`(커밋하지 않음)

- **개수 늘리기 (2026-11-24 결정):** 36개는 키워드 기준점과 파서·청킹 확인에는 충분하지만, 32개에서 hit@5 0.06 차이는 질문 2개 차이라 모델·청킹 비교에는 적다. PR 6(임베딩 비교) 전에 **20개쯤 더 채워 55개 안팎**으로 만든다. 남은 초안 70개(대표이사·최대주주·배당이 대부분)를 이어서 채우는 대신 **틀을 늘려 종류를 넓힌다**: 감사인, 자본적정성 숫자(BIS 비율 등), 소송·제재, 사업 부문별 비중, 주요 위험요인(서술을 10개 이상으로). 파서 빈 칸 수정 뒤에 한다(정형표 정답 확인이 표에 의존)
  → **2026-11-25:** PR 6은 41개로 진행했다(모델 차이가 0.556 vs 0.861로 커서 결정에 지장 없음). 9a(하이브리드)처럼 1~2개 차이를 보는 비교 전에 늘린다.
  2차 틀 9개(`eval/draft.py`: capital_adequacy·solvency·ncr·asset_quality·segment·lawsuit·sanction·market_risk·liquidity_risk, usecases 질문 10·11)를
  `--templates … --per-template 4`로 뽑아 사용자가 `eval.review`로 확인 → 55~60개 목표. "위험요인"은 국내 사업보고서에 별도 섹션이 없어 주석의 시장·유동성위험으로 대신
- **Phase 4용 그래프 질문 (2026-11-24 결정, PR 5 뒤에 추가):** "표(ER)가 담지 못하는 것" 네 갈래를 평가 세트에 넣는다. 유형은 기존 `다중경로` 하나로 두고 새 칸 `graph_kind`(추론 / 계층 / 의미 / 통합)로 나눈다. 갈래마다 3개, 총 12개, phase 4. 정답은 Phase 2에서 검증한 DuckDB 관계 테이블(최대주주·임원·출자)에서 확인하고 근거 접수번호는 `source_rcept_no`에서 가져온다. 다만 "의미" 갈래(사명 변경·합병으로 이름이 바뀐 회사)는 연혁 글에만 있어 뷰어 확인이 필요하다. Phase 3 검색기는 이 12개에서 거의 0점이 나올 것이고, 그것이 그래프를 붙인 뒤 비교할 출발선이다
  | 갈래 | 뜻 | 질문 예 |

## 9. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| DART XML 형식이 보고서마다 달라 파서가 자주 깨짐 | 파서는 "제목·문단·표"만 보고 나머지 태그는 무시. 깨진 보고서는 건너뛰고 품질 검사에 수를 남김. 100% 파싱을 목표로 하지 않음 |
| 로컬 임베딩이 너무 느림 | 범위 축소(사업보고서 먼저) → 작은 모델 → API 임베딩 순으로 후퇴. 각 단계를 0009에 기록 |
| 전문검색 정밀도가 실제 원문에서 떨어짐(0004 한계) | 하이브리드에서 전문검색 가중치를 낮추거나 벡터만 사용. 0004에 추기 |
| LLM이 조각에 없는 내용을 말함 | 구조화 출력으로 인용 번호를 강제하고, 인용 없는 문장은 프로그램이 표시. 평가 세트에 "없는 질문" 포함 |
| Neo4j 컨테이너가 꺼져 있어 자산 실패 | 실패는 정상 상태로 취급. 재시도만 하고 알림은 Phase 4에서 |
| 개인정보(임원 생년월 등)가 원문·조각·평가 결과에 들어감 | `data/`, `eval/results/`는 커밋하지 않음. 테스트 fixture는 개인정보 없는 섹션만 잘라 쓴다 |

## 10. 하지 않는 것

- 질문에서 회사·연도를 자동 추출(1차는 CLI 옵션). 평가 결과를 보고 2차에서 판단
- 웹 UI. CLI로 충분히 평가할 수 있다
- 감사보고서·수시공시 원문. 정기보고서로 지표가 나온 뒤 범위를 넓힌다(0002의 "다시 판단할 조건"과 같은 방식)
- Phase 4의 그래프 탐색. 다만 노드에 `corp_code`를 붙여 이어 갈 수 있게 한다

## 11. Phase 4 그래프 스키마의 방향 (2026-11-24 사용자 결정, 결정 문서는 0011로 Phase 3 뒤에)

온톨로지를 새로 발명하지 않는다. Phase 2에서 검증한 DuckDB 테이블(최대주주·임원·출자·사람)이 뼈대이고, 그래프는 그것을 노드·관계로 옮긴 뒤
"표가 못 하는 것"(경로 탐색·계층·같은 것 묶기)을 더한다. 평가 세트의 그래프 질문 12개(추론·계층·의미·통합, 4절)가 이 스키마의 시험지다 —
질문을 먼저 만들고 스키마가 그 질문에 답할 수 있는지 확인하는 순서로 가서, 설계가 질문보다 커지지 않게 한다.

- **노드 4종:** `Corp`(corp_code. 이름으로 잇지 않음) · `Person`(person_id = 이름|생년월|성별, 0006) · `Document`(rcept_no) · `Chunk`(chunk_id, Phase 3에서 먼저 생김)
- **관계 5종**, 모두 `valid_from`·`valid_to`·`source_rcept_no`를 단다(0005 이중 시간축. "그 시점 그래프"를 필터 하나로):
  `(Corp)-[OWNS {지분율, 주식 수, 장부가액}]->(Corp)`(출자·최대주주), `(Person)-[HOLDS_POSITION {직위, 등기 여부, 사외이사 여부}]->(Corp)`,
  `(Corp)-[FILED]->(Document)`, `(Document)-[HAS_CHUNK]->(Chunk)`, 사명 변경·합병은 `FORMERLY` 관계 또는 이름 이력 속성
- **세 층:** 사실(공시 값 그대로, 위 전부) / 파생(규칙 계산: 간접 지분율, 지배 판정, 겸직 네트워크. 관계마다 `derived_from`·`rule`) /
  해석(LLM 판단. 그래프에 넣지 않고 답변 단계에서만) — 추측이 데이터에 섞이지 않게
- **설계 전에 조사 문서.** 0011을 쓰기 전에 `docs/plans/phase4-research.md`(Phase 3의 `phase3-research.md`와 같은 역할)를 먼저 쓴다(사용자 제안 2026-11-25).
  주제: GraphRAG 계열(Microsoft GraphRAG·LightRAG·G-Retriever — "검색 뒤 그래프 탐색" 부분만, LLM 관계 추출은 쓰지 않음), 금융 문서의 벡터+그래프 하이브리드(어느 질문에서 그래프가 이득이었나),
  시간 그래프(temporal/bitemporal KG — 0005 이중 시간축과 맞춰 보기), 도구(neo4j-graphrag `VectorCypherRetriever`). 웹에서 확인한 것만 적고 설계에 반영한다
  사용자가 준 후보 자료(2026-11-25, **원문 미확인 — 조사 문서 쓸 때 하나씩 확인**): Agentic GraphRAG for Financial Data(ETH, 2026-04, arxiv 2605.18770 — 정형 필드는 규칙으로 "강한 노드",
  비정형 글은 LLM으로 "약한 노드"; 우리 세 층과 같은 발상이되 약한 노드를 그래프에 넣는 점이 다름 → 넣되 구분 표시가 나은지 다시 본다), FinKario(ACL 2026 — 리포트 기반 이중 구조 KG, 갱신 속도),
  FinReflectKG-HalluBench(2026-03, arxiv 2603.20252 — 금융 GraphRAG 환각 측정; 답변 평가 지표에 참고), Knowledge Graph Construction for Stock Markets(CIKM 2025 WS, arxiv 2601.11528 — 한국 연구진, 주식시장 KG 스키마),
  Zep/Graphiti(neo4j 블로그 — 에이전트 장기 기억용 bi-temporal KG: 엣지마다 t_valid/t_invalid, 충돌은 지우지 않고 무효 처리. **우리 0005와 같은 모델**(valid_from/valid_to·source_rcept_no/superseded_by, 이미 구현·검증). 다른 점은 입력이 LLM 추출인 것.
  Phase 4에서는 Neo4j 엣지 시간 속성과 시점 필터 Cypher 패턴을 참고), FinSage(arxiv 2504.14493 — 공시 QA에서 GraphRAG·LightRAG가 기대에 못 미친 반대 사례; "그래프가 어느 질문에서 이득인지 먼저 정한다"는 우리 순서의 근거), Graph-Assisted LLMs 서베이(ACL 2026 Findings), KG-LLM 워크숍 @ LREC 2026(Text2Cypher 신뢰도, GroundedKG-RAG)
- **FIBO는 참고 어휘로만.** 0011에 "우리 관계 ↔ FIBO 용어" 대응표 한 절 (research 5절의 판단)
